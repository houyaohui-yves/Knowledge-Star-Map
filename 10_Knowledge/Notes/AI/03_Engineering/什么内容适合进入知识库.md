# 什么内容适合进入知识库

## 核心认识

判断一份内容是否应进入知识库，先明确知识库服务谁、为了什么。个人学习沉淀、生产 RAG 的证据管理，以及向量索引建设，是三个不同的判断，不能用同一套准入条件混为一谈。

| 判断 | 主要标准 | 不应误设的必要条件 |
| --- | --- | --- |
| 是否值得个人沉淀 | 帮助理解、纠正误区、连接已有知识、保留重要依据或支持未来行动 | 不要求模型不知道，也不要求已经完全掌握 |
| 是否适合用 RAG 提供证据 | 任务需要外部依据，资料规模、更新、检索收益与成本相匹配 | 不要求每份资料都反复使用；一次性长文档也可能需要检索 |
| 是否需要向量索引 | 语义匹配是否有用，模型与任务是否适配 | 入库不等于必须向量化，精确查询可能更适合 SQL 或关键词 |

在本项目中，即使模型熟知 Embedding，你刚形成的理解、容易混淆的边界和必要例子也值得记录。未核实片段可以进入 Sources 或 Inbox，已经整理的知识可以处于 `developing`；不能因为保存了笔记就标记自己已掌握。

以下六个问题主要用于生产 RAG 的知识准入，是工程判断清单，不是所有个人知识都必须通过的门槛。

## 面向生产 RAG 的六个判断问题

### 1. 是否会被反复使用

如果多个用户、多个任务或多个时间点都会再次需要这份信息，建立知识库通常有价值。只用于一次请求、内容很短且不会复用时，直接放入当前 Prompt 往往更简单。

但“不复用”不等于“不保存”或“不检索”：重要决策可以因追溯价值保留；一次性超长材料也可能建立临时索引。保存价值与检索投入要分别判断。

### 2. 模型能否可靠地自行知道

私有制度、内部 SOP、本地产品资料、最新政策、团队决策和专有术语通常不在模型参数中，或模型可能记错、过时，因此适合通过外部知识提供。

公开且稳定的常识不一定值得为生产问答重新建库，除非任务要求特定口径、版本或引用；这不妨碍个人为了学习而整理它。“模型不知道”是外部知识的常见价值来源，不是入库必要条件。

### 3. 是否有明确且可信的来源

知识应尽量能够回答：谁发布、何时生效、适用范围是什么、原文在哪里、当前版本是什么。未经核实的传言、聊天猜测和互相冲突的草稿不应直接成为生产知识，可以先进入待验证区。

### 4. 是否能够持续维护

需要明确负责人、更新触发条件和失效机制。频繁变化却没人同步更新的内容进入知识库后，可能比没有知识更危险，因为系统会稳定地返回过期答案。

### 5. 是否能够形成可检索的证据单元

内容应该能够切分或建模成相对独立、可理解、可追溯的事实、规则、流程、案例或问答。只有大量重复文字、脱离上下文无法解释的片段，或必须依赖整份文档才能理解的内容，需要先重新组织。

### 6. 是否允许被当前用户和系统使用

隐私、商业秘密、个人信息和受版权限制的材料只有在权限、保存范围和访问控制清楚时才能进入。知识库与检索索引都需要同步权限，不能只限制原文件而让 Chunk 或 Vector 被越权召回。

## 典型适用内容

- 企业规章制度、操作流程和客服 SOP；
- 产品手册、技术文档、API 文档与故障处理记录；
- FAQ、经过审核的标准答案和真实案例；
- 私有领域术语、业务规则和组织内部口径；
- 课程、研究资料与经过整理的个人学习知识；
- 已确认的会议决策、行动项、负责人和截止时间；
- 需要引用来源、版本或生效日期的专业资料。

这些内容仍需经过清洗、版本处理、权限标注和质量检查，不能因为属于上述类别就全部无差别导入。

## 不宜直接做成向量知识库的内容

| 内容类型 | 主要问题 | 更合适的处理 |
| --- | --- | --- |
| 一次性、很短的临时材料 | 建库与维护成本高于复用价值 | 直接放入当前 Prompt |
| 未核实的猜测或草稿 | 容易被系统误当成事实 | 待验证区、审核后再发布 |
| 实时库存、价格和账户余额 | 更新频率高，向量索引容易过期 | 实时 API 或业务数据库 |
| 精确数值统计与条件筛选 | 向量相似度不能保证精确计算 | SQL、分析系统或代码 |
| 必须严格执行的业务规则 | LLM 解释可能产生不确定性 | 规则引擎、决策表或工作流 |
| 大量重复、失效或冲突版本 | 造成召回污染与答案冲突 | 去重、归档、确定版本优先级 |
| 没有权限边界的敏感资料 | 可能泄露隐私或机密 | 先完成权限与合规设计 |

“不宜直接做成向量知识库”不等于不能成为系统知识。它可能更适合放在关系数据库、规则系统或实时服务中，再由应用按需查询。

## 根据问题选择知识表示

| 需求 | 更合适的知识形态 |
| --- | --- |
| 用户用自然语言查找文档含义 | 文本 Chunk、关键词与向量混合检索 |
| 按价格、日期、状态精确过滤 | 结构化字段、SQL 或 Metadata Filter |
| 查询实体间关系 | 图结构或显式关系表 |
| 执行合规判断和确定性规则 | 规则引擎或决策表，并附原文证据 |
| 获取实时状态 | API 或业务数据库 |
| 模仿特定任务的正确做法 | 高质量输入—输出样例库 |
| 回答常见问题 | 标准 Question、扩展 Question 与可追溯 Content |

成熟的知识系统通常同时使用多种表示，而不是把所有内容都转换成向量后交给同一种检索器。

## 一个简化的生产 RAG 准入流程

```text
本次任务是否需要外部依据？
  否 → 不必为了该任务建检索库；个人保存价值另行判断
  是
  ↓
资料很短且只用一次？
  是 → 可直接提供上下文；需追溯的材料另行保存
  否 → 结合规模、更新与使用频率评估检索或临时索引
  ↓
是否有可信来源和明确适用范围？
  否 → 先验证，不发布为正式知识
  是
  ↓
是否有人负责更新、失效和权限？
  否 → 先补治理机制
  是
  ↓
用户将怎样查询和使用它？
  文本语义 → 关键词 / 向量检索
  精确条件 → SQL / Metadata
  实时状态 → API
  确定规则 → 规则引擎
```

知识准入不仅决定“收不收”，还应决定它的权威级别、更新时间、访问权限、检索方式和无法回答时的行为。

## 重要误区

- 文件已经存在，不代表它适合直接进入知识库。
- 能够生成 Embedding，不代表向量检索是最适合的访问方式。
- 内容越多不代表覆盖越好；低质量、重复和过期资料会污染召回。
- 生产知识库应有与风险相称的审核、版本、权限和退出机制；个人知识库可以轻量管理，不应照搬企业治理负担。
- RAG 适合为模型提供证据，不应代替需要确定执行的数据库、计算代码和规则系统。
