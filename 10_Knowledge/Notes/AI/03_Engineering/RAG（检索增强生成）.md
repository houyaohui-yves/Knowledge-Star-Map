# RAG（检索增强生成）

> 原题为“读取文件(检索增强生成 RAG)”，2026-10-03 按核心概念更名并迁移链接。RAG 不等于“读取文件”，知识源也可以是数据库或搜索服务。本篇维护主流程，专题阅读顺序与优化方法入口见 [[提示词与RAG：学习地图]]。

## 核心认识

RAG 的全称是 **Retrieval-Augmented Generation**，中文通常译为“检索增强生成”。它的基本思想是：在生成答案之前，先从外部知识源检索与当前问题相关的信息，再把检索结果放进模型的上下文，让模型基于这些信息完成回答。

通俗地说，可以把它理解成“先查资料，再回答”。但“内部知识搜索”容易产生误解：经典 RAG 的知识库位于模型参数之外，检索通常由应用程序或检索服务完成，并不是 LLM 在自己的参数记忆中搜索。

RAG 主要解决两类矛盾：

- 模型的上下文窗口有限，不能在每次请求中放入全部资料。
- 模型参数中的知识可能缺失、过时，或无法覆盖私有资料；外部知识库可以独立更新。

## 与 In-Context Learning 的关系

In-Context Learning（上下文学习）指模型在不更新权重的情况下，根据当前上下文中的指令、信息或示范完成任务。Few-Shot 示例是它最典型的形式。

把参考资料放入 Prompt 可以广义地看作利用上下文影响模型，但工程语境中也常称为 context augmentation；不能简单地把任何“Prompt 中存在资料”都等同于 Few-Shot。RAG 的重点不只是把资料放进上下文，而是根据当前问题**动态检索**少量相关资料，再用于生成。

上下文窗口长度是硬限制；在限制之内，过多无关、重复或相互冲突的内容还会增加成本，并可能让关键信息被忽略。因此知识库的作用不是无限扩展 Prompt，而是为每次任务筛选更合适的上下文。

## 两个宏观阶段

从整体上看，RAG 可以分成两个大阶段：

1. **离线建库（Indexing）**：把原始资料处理成可被检索的知识单元并建立索引。
2. **在线使用（Retrieval and Generation）**：根据用户问题检索相关知识，组装 Prompt，再由 LLM 生成结果。

“模型调用知识库”是便于理解的简称。经典实现中，更准确的调用关系通常是：应用程序访问知识库并获得检索结果，然后把结果连同用户问题提交给模型。在工具调用等实现中，模型也可以参与决定何时检索，但实际访问仍需由相应系统执行。

## 离线建库：Indexing

Indexing 是整个建库阶段的总称，不只是把文件转换成纯文字。典型流程是：

```text
收集资料 → 解析与清洗 → 切片 → 添加元数据 → 建立检索表示与索引 → 存储
```

### 1. 收集、解析与清洗

- 收集 PDF、网页、Word、数据库记录等资料。
- 通过文本解析或 OCR 提取内容，并清除无关页眉、乱码和重复内容。
- 尽量保留标题层级、表格、页码、原始文件标识等结构与来源信息，而不是只留下失去出处的纯文本。

### 2. Chunking

Chunking 把长文档拆成能够独立检索和理解的知识切片。可以用代码按长度切分、按标题和段落切分、借助模型进行语义切分，也可以人工调整关键资料。

“几百字到两千字”可以作为某些中文材料的初始经验值，但不是通用标准。工程上通常还要考虑 Token 数量、文档结构与任务需要：

- 切片太大：可能混入多个主题，向量表达变得模糊，并浪费上下文。
- 切片太小：容易丢失上下文，使信息无法独立解释。
- 相邻切片可以保留适度重叠，也可以在检索后补回标题、父级段落或相邻内容。

每个 Chunk 应尽量保留来源、文档 ID、标题、页码、时间等元数据，以便过滤、追溯和引用。

长文档或会议记录可以通过 LLM 寻找主题边界，并使用父主题与子 Chunk 保留层级关系。具体方法见 [[RAG中的长文档语义切片]]。

### 3. Vectorize & Store

[[Embedding(嵌入)]] 模型把一段文本映射为高维数学向量，使语义相近的文本在向量空间中通常也更接近。系统对每个 Chunk 生成向量，并把向量、原文和元数据一起保存。

向量数据库是常见方案，但不是 RAG 的必要条件。向量可以存入专用向量数据库，也可以存入带向量索引能力的普通数据库；系统还可以使用关键词倒排索引、SQL 查询或搜索 API。向量检索与关键词检索结合的方式通常称为混合检索。

知识库是被管理的知识整体，向量数据库只是常见的向量检索组件，二者的概念边界见 [[知识库与向量数据库]]。

## 在线使用：Retrieval and Generation

典型运行流程是：

```text
用户问题
  → 查询处理与向量化
  → 从索引中召回候选 Chunk
  → 过滤或重排
  → 组装 Prompt
  → LLM 生成答案
```

### 1. 查询与召回

用户问题（Query）会使用与文档向量兼容的嵌入模型和配置转换成查询向量。系统再根据余弦相似度、点积或其他距离度量，找出向量上最接近的若干 Chunk。

这里得到的是“语义上相近的候选项”，不一定就是最终最有用的证据。实际系统还可能加入元数据过滤、关键词检索、查询改写和重排模型，以提高相关性。

### 2. 拼接 Prompt

应用通常通过代码和预先设计的 Prompt 模板，把以下内容组装成一次完整请求：

- 系统要求和回答规则；
- 检索得到的相关 Chunk，最好带有来源标识；
- 用户的原始问题；
- 输出格式、引用或无法回答时的处理要求。

可以概括为：

```text
最终 Prompt = 固定指令 + 检索上下文 + 用户问题 + 输出约束
```

然后应用把这个请求发送给 LLM。模型依据提供的上下文组织答案，但“把资料放进 Prompt”并不会自动保证答案正确；检索质量、上下文组织方式和生成约束仍然需要分别评估。

## 重要边界与误区

- RAG 的“检索”通常发生在模型外部，不是搜索模型参数里的内部知识。
- Indexing 是解析、切片、建立索引和存储的完整流程，不只是文本提取。
- Chunk 没有适用于所有材料的固定字数，需要按文档结构和任务评估。
- RAG 不必使用向量数据库；关键词、结构化查询和混合检索同样可以参与。
- 向量最相似只意味着适合作为候选，不保证它足以回答问题。
- LLM 通常不会直接调用知识库，负责串联检索与生成的是应用编排层。
