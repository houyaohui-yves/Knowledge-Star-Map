# RAG中的Embedding模型选择与评测

## 核心认识与范围

为 RAG 选择 Embedding，就是选择怎样把 Query 和知识块编码到兼容、适合检索的空间。模型生成表示，[[向量数据库]] 保存和搜索表示；两者需要配合，但数据库品牌本身通常不决定唯一可用模型。

先按任务、语言、部署约束筛选少量候选，再用同一批业务问题与文档比较检索质量、延迟和成本。向量维度、模型参数量、文件大小、公共榜单总分，都不能单独决定优劣。表示原理见 [[Embedding(嵌入)]]；统计与学习表示的路线选择见 [[文本表示方案的选择：TF-IDF、词向量与句子向量]]，本页聚焦已决定使用文本 Embedding 后的具体选型。

下列是代表性模型及核对过的版本，不是完整清单、实时排行榜或本项目实测推荐。官方页面查阅于 2026-10-03；具体部署前仍应检查模型修订、配置及服务可用性。

## 常见模型与具体版本

| 系列／模型 | 代表版本与已核对事实 | 可考察的方向与边界 |
| --- | --- | --- |
| BGE 中文系列 | [BAAI/bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)：512 维；同系列中文 base／large 为 768／1024 维 | 中文检索的候选；small、base、large 的资源与质量取舍要实测。中文 small 与英文 small 的维度不同，不可只按系列名配置索引。 |
| BGE-M3 | [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3)：稠密表示为 1024 维、序列长度 8192；同时支持稠密、稀疏及多向量检索表示 | 多语言、较长输入及混合检索候选。仅提取 `dense_vecs` 并写入单一稠密索引，不等于已实现三种检索的融合。 |
| M3E | [moka-ai/m3e-base](https://huggingface.co/moka-ai/m3e-base)：768 维，模型卡说明中文／英文及句对相似性、查询—段落检索用途 | 可作为中文为主任务的对照。历史模型卡分数不作为今天的统一排名，也不证明法律、医疗等专门领域效果。 |
| GTE | [Alibaba-NLP/gte-Qwen2-1.5B-instruct](https://huggingface.co/Alibaba-NLP/gte-Qwen2-1.5B-instruct)：1536 维、32k 输入；[7B 版本](https://huggingface.co/Alibaba-NLP/gte-Qwen2-7B-instruct)为 3584 维、32k 输入 | 多语言、指令驱动检索候选；查询侧使用相应任务指令。1.5B 与 7B 是不同模型，不能混用向量或互相继承性能结论。 |
| E5 | [intfloat/multilingual-e5-large](https://huggingface.co/intfloat/multilingual-e5-large)：1024 维，多语言，长文本截断至最多 512 tokens；[e5-mistral-7b-instruct](https://huggingface.co/intfloat/e5-mistral-7b-instruct)：4096 维，官方建议用于英文且不建议输入超过 4096 tokens | 需按具体版本选语言和编码方式。E5 家族不能统一当成英文或多语言，也不能统一套用一套前缀。 |
| Qwen3 Embedding | [Qwen/Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)：最多 1024 维、32k 输入，支持多语言、任务指令与可配置输出维度；系列另有 4B／8B | 多语言检索及不同资源配置的候选；名称中的 Embedding 与 Qwen 通用聊天模型有不同任务职责，重排序型号也不能当成编码型号。 |
| Jina Embeddings | [jinaai/jina-embeddings-v2-base-zh](https://huggingface.co/jinaai/jina-embeddings-v2-base-zh)：中英双语，支持 8192 序列长度 | 中英混合输入的候选；具体版本、下载访问条件与使用方式需查看模型卡，不把某个 small 型号延迟推广给全系列。 |
| Sentence Transformers 常用小模型 | [sentence-transformers/all-MiniLM-L6-v2](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2)：英语模型、384 维，默认超过 256 word pieces 截断 | 英文短文本、小规模 CPU 试验的对照候选。Sentence Transformers 是工具库／模型生态，不是一个统一模型，也不能由能接收中文推断中文效果合适。 |
| 托管 API 示例 | [OpenAI text-embedding-3-small／large](https://developers.openai.com/api/docs/guides/embeddings)：默认 1536／3072 维，支持通过 `dimensions` 指定较小维度 | 可直接调用 API，无需自己部署推理硬件。服务调用与下载开源权重自行部署是不同路径；具体计费、限流和访问能力以服务文档为准，本页不保存动态价格。 |

输入长度是模型配套 Tokenizer 下的限制，不是中文字数、整个知识库容量或最优分块长度。还需检查推理库实际配置的 `max_seq_length`：它可能低于模型能力上限，导致静默截断。

## 选型要回答的六个问题

1. **任务是什么？** Query—文档检索、文档互比、聚类、分类有不同关系标准。RAG 应优先考察相关语言的 Retrieval 分项，而非只看相似句子的分数或综合榜首，见 [[MTEB（文本嵌入评测）]]。
2. **语言与领域是否适配？** 除中文／英文，还要检查混合语言、业务术语、编号、型号、否定、条件与新旧版本等实际查询。专用领域效果必须有对应数据支持。
3. **块长与编码配置是否适配？** 看 Token 限制、截断位置、Query／Document 指令、Pooling、归一化与相似度。长度更大的型号不免除 [[RAG中的长文档语义切片|分块设计]]。
4. **资源与成本能否接受？** 区分首次全量编码、后续增量编码和在线 Query 编码；分别测吞吐、单次延迟、内存／显存和 API 成本。较大输出维度还增加存储与搜索成本，见 [[RAG与向量检索的容量与性能]]。
5. **部署与数据流是否符合需求？** 区分托管 API、自行租云服务器部署、企业内网部署。若要求全流程留在内网，Embedding、重排、生成、外部工具和日志都要检查，不能只看向量库位置。
6. **如何维护与替换？** 保存精确模型 ID、修订版本、Tokenizer、Query／Document 编码规则、长度、维度、归一化、距离尺度及推理精度；将这些配置与索引关联。替换模型通常需要重新编码文档、建立新索引并回归验证。

向量维度影响兼容性与成本，但不是“理解深度”的直接刻度。模型参数量影响推理资源，输出维度影响向量存储，两者是不同量；课件中的权重文件大小也不能直接当成运行显存需求。

## 为什么试用时要遵循各自的编码方式

| 具体模型 | 已核对的调用差异 |
| --- | --- |
| multilingual-e5-large | 检索时查询添加 `query: `，文档添加 `passage: `，非英文文本也采用这些前缀。 |
| gte-Qwen2-instruct | 查询侧使用任务指令，Sentence Transformers 示例采用 `prompt_name="query"`；文档侧不加同样指令。 |
| Qwen3-Embedding | 官方示例在查询侧采用任务提示；文档侧不添加相同检索指令。 |
| BGE-M3 | 官方说明不需要为查询额外添加 BGE 早期型号使用的指令。 |

这些差异来自对应模型卡，不能统一给所有模型加一种前缀。自己用底层 Transformers 实现时，还需复现模型要求的汇聚和归一化；“取某个隐藏向量”不自动等于官方文本表示。

两套模型的相似度分数不可直接用来证明谁更好。例如同一个查询，A 给正确文档 0.8、B 给它 0.7，不能推出 A 更强；需要看各自在完整候选集中的排序与相关性。此处数字是助手教学构造，不是实际模型输出。不同模型的阈值也需分别校准。

## 两条部署 Tips 的校准

用户建议“每样试一下、可以到 AutoDL 租 GPU”，可以作为实验路径，但不必遍历所有模型。先筛选 2–3 个满足条件的候选，更便于控制变量和预算。也可以先在本机运行小模型，或在允许数据外发时调用托管 API。

[AutoDL 官方计费说明](https://www.autodl.com/docs/price/)的容器实例按量规则按开关机时长计费，使用时长精确到秒，并在整点与关机时扣费。因此“按小时计费”适合作为粗略理解，不应理解成必须整小时购买，或只在 GPU 正在计算时收费。付费扩容数据盘另计；停计算任务不等于关闭实例，关闭实例也不等于所有存储费用停止。此为 2026-10-03 查阅到的规则，实际租用前核对对应实例类型与现价；本轮未租用或产生费用。

“私有化部署需要有 GPU 的电脑”过于绝对。更准确的说法是：**需要企业控制环境中的兼容运行时和足够资源；GPU 是否必需，由具体模型、实现与服务目标决定。**

- 小模型、小数据或低并发可以使用 CPU；Sentence Transformers 明确支持 CPU，部分型号可用 ONNX／OpenVINO 等后端优化。
- 全量批量编码、较大模型、长输入或高并发常更适合 GPU；不能只按模型下载文件大小选显存，还要考虑输入长度、批量大小、精度、运行开销和其他服务。
- 自行部署通常是下载已有权重进行推理，不等于从头训练或微调。权重、Tokenizer、配置、依赖与模型使用条件也需要配套准备。
- 向量库的存储与近邻搜索不因 Embedding 用 GPU 而必须用 GPU，两类资源分开规划。云服务器上自己运行开源模型也仍使用云环境；是否满足企业的私有化要求需按部署与数据边界判断。

CPU 支持与优化依据：[Sentence Transformers：Speeding up Inference](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html)。未在本机测量上述型号的 CPU／GPU 性能，不能保证特定硬件达到业务延迟。

## 一个可执行但尚未运行的比较设计

以下是助手的实验建议，样本规模是入门起点，不是统计充分性保证：

1. 选择少量候选，例如中文小模型 BGE-small-zh、BGE-M3，以及 Qwen3-Embedding-0.6B；受资源约束时可以只测两种。此组合用来观察取舍，不预设谁获胜。
2. 用同一份文档、版本、块 ID、分块和查询建立测试数据。准备几十至一百条有代表性的问题，人工标注相关证据块；覆盖近义表达、型号、条件、否定、跨语言及库内无答案等情况。
3. 各模型遵循自己的正确编码规则，为同一批文档分别建独立索引。检查每块实际 Token 数与截断；第一轮可选择候选都能容纳的块，另记录长块表现，不能把截断损失隐去。
4. 第一轮不加重排序或生成模型，尽量使用精确向量搜索，先检查表示本身的候选排序；再接入相同检索链路，测近似索引与 Rerank 的整体影响。
5. 在有答案问题上，比较 Recall@K（已标注相关块被找回的比例）、Hit@K（前 K 名至少命中一个相关块的问题比例）和 nDCG@K（考虑相关程度与排名的质量）。分别统计无答案问题的误命中或拒答策略表现，不把它们强塞进分母为零的 Recall。
6. 同时记录批量编码吞吐、在线查询延迟、峰值内存／显存、向量体积和成本；区分冷启动、预热后结果及输入长度。调参数据与最后验证数据分开。
7. 第一轮保持其他条件一致以定位差异；第二轮允许各候选调整适合自己的分块和索引，比较最终方案。后一轮的提升应归为整套方案效果，不能全部归功于模型。

教学例子：问“L2 可以无线连接吗？”，标注证据应是 L2 的连接方式说明。返回 L1 的无线说明或 L2 的保修说明只说明主题相关，不能算命中了正确证据。最终回答还需另查 [[检索重排序（Rerank）]] 与 [[RAG的失败诊断与反馈迭代]]，不把召回指标直接等同于答案准确率。

## 课件表述的边界与待核验部分

- 学习出处是本章第 9–18 页，以及用户本轮提出的试用／私有化 Tips。上述模型卡事实、CPU 边界和比较设计是助手补充，不冒充课件原意。
- 第 11 页 Jina small 的 `RT<50ms` 没有硬件、批量、输入长度和后端条件；M3E 对法律／医疗的场景评价缺少本课程实验，不作为性能或领域保证。本页核对的 Jina 型号为 `v2-base-zh`，不是课件 small 型号。
- 第 12 页的“企业级”是应用部署语境，不是另一类统一模型架构；“动态调整语义密度”缺少明确操作与指标，本轮不提升为知识结论。
- gte-Qwen2 的官方用法编码 Query／Document 后计算相似度；名字中的 `instruct` 表示指令驱动的表示用途，不据此认定这个 Embedding 型号负责生成自然答案或多步推理。PDF 第 15–17 页的 1.5B 与第 18 页的 7B 要分开对应。
- 课件另列 xiaobu-embedding-v2、stella-mrl-large-zh-v3.5-1792；本轮未核对其官方权重版本、输入配置与性能，只保留为待查候选，不把课件宣传写成已验证推荐。
