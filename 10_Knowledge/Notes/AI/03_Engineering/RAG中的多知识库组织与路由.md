# RAG中的多知识库组织与路由

## 核心认识

实际应用可以按业务领域组织多个知识源，再按任务选用，但不必一开始就部署多个数据库。是否分开要看管理、权限、更新、表示与检索需求；数据多本身不决定“多知识库 + LLM Workflow”架构。

| 层次 | 说明 | 例子 |
| --- | --- | --- |
| 业务知识域 | 人怎样管理内容与责任 | 人事制度、财务制度、产品手册 |
| 检索逻辑分区 | 服务怎样划定候选范围 | Metadata 过滤、Namespace、Collection、不同索引；各产品语义不同 |
| 物理部署 | 数据存在哪里、资源如何隔离 | 一个数据库／集群承载多个领域，或多个独立服务 |
| 分片与副本 | 同一集合如何扩容与容错 | 一个知识域的数据横跨多个节点 |

这些层次不能互换：多个业务库可以共用一个数据库；一个业务库也可以跨多个存储分片。Collection 不自动等于独立物理机器或完整安全边界。

## 如何选择组织方式

| 当前需求 | 可考虑的方案 | 代价与注意点 |
| --- | --- | --- |
| 同一种表示、共用运维，只需区分领域／租户 | 同库保存字段并过滤，给过滤字段建适合的索引 | 应用必须正确校验与施加过滤，字段本身不提供授权 |
| 不同生命周期、配置或有限数量的隔离需求 | 不同集合／索引 | 会产生资源与管理开销，按产品能力验证 |
| 强资源或部署隔离、不同地域或后端 | 独立服务 | 跨源查询、更新、备份与故障处理更复杂 |
| 仅因规模增长需要扩容 | 存储分片、压缩或扩容 | 不一定需要改变业务知识域划分 |

不同模型得到的向量即使维度相同也未必可比，可能需要独立索引或不同命名向量；每个查询按各自兼容编码处理。不能把不同库的原始相似度直接混排。

## Router 与 Workflow 怎样参与

Router 回答“本次需要哪些知识源／检索器”，Workflow 负责执行选路、调用、合并、生成与异常处理。Router 可由固定规则、界面选择、分类模型或 LLM 实现，不一定要用 LLM，也不一定需要独立可视化平台。

一个固定代码流程同样可以实现：

```text
身份与访问范围校验
→ 识别实体、领域与子问题
→ 选择一个或多个允许访问的知识源
→ 按各源配置检索
→ 合并、去重、重排与证据覆盖检查
→ 组装上下文并回答
```

多源可并行，也可分步检索；如果第二步依赖第一步结果，应保持顺序。访问范围由应用确定，LLM 路由只是业务选择，不能赋予用户新的权限。输入不足时澄清，不应把所有请求都强行归到唯一类别。

## 跨领域教学例子

假设企业助手有“财务制度”“产品手册”“人事制度”三类知识。用户问：“维修星灯 L2 的费用可以报销吗？”此例是助手自拟，未部署。

1. Router 识别需要产品的保修条件与财务的报销条件，选择产品和财务两路；不因“费用”一词只查财务。
2. 产品检索查当前 L2 保修／维修规则，财务检索查维修费用报销的适用范围及审批条件。
3. 合并证据时保留来源、日期和对象；若缺少购买时间、费用原因或票据条件，说明需补充，不能从“能保修”直接推出“能报销”。
4. 如果其中一源故障或无证据，应保留可确认的部分并说明缺失，不以另一路材料编造结论。

路由能减少无关候选和部分成本，也会引入“选错库导致资料永远没被检索”的失败点。对跨领域问法、模糊问题与漏路由做独立评测；“分类置信度高”不等于证据完整。

## 多路结果怎样合并

同一问题从多个源召回后，按稳定 ID 去重，保留全部可追溯来源，检查版本与覆盖，必要时以统一模型对正文重排。不同库、模型或距离的分数不一定同量纲；可使用基于排名的融合或统一评分，但策略需实际评估。这里只给出方向，不把未测试融合方法写成必然改善。
