# 知识库与向量数据库

## 核心认识

知识库是“被组织和管理的知识整体”，向量数据库是“保存向量并执行相似度检索的技术组件”。在简单 RAG 产品中，两者有时被口语化地混称为“知识库”，但它们解决的问题、包含的内容和生命周期并不相同。

可以用图书馆来类比：

- **知识库**像图书馆整体，包括书、章节、分类、版本、来源和借阅权限。
- **向量数据库**像一套能够按“意思相近”查找候选书页的检索目录。

目录可以帮助找到资料，但不负责保证资料本身权威、完整、最新或足以回答问题。

## 什么是知识库

知识库（Knowledge Base）是面向某个领域或任务管理知识的逻辑系统。一个 RAG 知识库可能包括：

- PDF、网页、制度、FAQ、数据库记录等原始资料；
- 解析和切分后的 Content / Chunk；
- 标准 Question、合成 Question、摘要和结构化字段；
- 来源、作者、版本、生效时间、页码和权限等元数据；
- 文档之间的关系、父子 Chunk 和相邻关系；
- 更新、审核、删除、追溯和质量评测机制；
- 用于访问这些内容的关键词索引、向量索引、SQL 或图查询。

因此，知识库描述的是“有哪些知识、怎样组织、由谁维护、是否可信以及怎样被使用”，并不限定必须采用哪一种数据库。

知识库可以只由文件、Wiki 或关系数据库构成，也可以同时使用搜索引擎、图数据库和向量数据库。

并不是所有资料都值得进入知识库；应先判断复用价值、来源可信度、更新机制、可检索性和权限。具体准入原则见 [[什么内容适合进入知识库]]。

## 什么是向量数据库

向量数据库（Vector Database）是为高维向量的保存、索引和近邻搜索而设计的存储与检索系统。它通常提供：

- 保存 Embedding Vector；
- 根据余弦相似度、点积或距离进行 Top-K 近邻搜索；
- 建立近似最近邻索引以提高大规模搜索速度；
- 使用业务、权限、时间等 Metadata 过滤候选；
- 保存向量与 `chunk_id`、`document_id` 或其他 Payload 的映射。

[[Embedding(嵌入)]] 模型负责把文本、图片等内容转换成向量；向量数据库主要负责保存、索引和搜索这些向量。某些产品把嵌入能力集成在一起，但两个概念仍然不同。

向量数据库也不只服务于知识库。图片搜索、商品推荐、用户兴趣匹配和异常检测都可以使用向量数据库，而不一定构成知识库。

## 核心区别

| 维度 | 知识库 | 向量数据库 |
| --- | --- | --- |
| 概念层级 | 面向业务和知识管理的逻辑系统 | 面向向量存储与检索的基础设施 |
| 核心目标 | 管理可用、可信、可追溯的知识 | 快速寻找向量上相近的候选项 |
| 主要内容 | 原文、Chunk、问答、结构、来源、版本、权限 | Vector、ID、Payload 和过滤 Metadata |
| 主要能力 | 组织、更新、审核、追溯、权限和多种检索 | 向量索引、相似度搜索和元数据过滤 |
| 是否必须依赖对方 | 可以不用向量数据库 | 可以存储与知识无关的向量 |
| 是否判断事实正确 | 需要在知识治理层保证 | 不能；相似度不等于正确性或权威性 |

## 二者在 RAG 中如何连接

一个典型的结构是：

```text
原始资料
  ↓ 解析、清洗、切片和知识加工
知识库记录：Content + 来源 + 版本 + 权限 + Metadata
  ↓ Embedding
向量数据库：Vector + chunk_id + 可过滤 Metadata
  ↓ Query Vector 相似度检索
候选 chunk_id
  ↓ 回到知识记录并获取 Content
Content 进入 Prompt
  ↓
LLM 生成答案
```

在 `question-content` 方案中，可以具体表示为：

```text
知识库：
  answer_id / chunk_id
  content
  canonical_question
  synthetic_questions
  source / version / permissions

向量数据库：
  question_vector
  question_id
  chunk_id
  filter_metadata
```

运行时，用户 Query Vector 匹配 Question Vector，检索结果通过 `chunk_id` 找到知识库中的 Content，再把 Content 放进 Prompt。

有些向量数据库允许把 Content 作为 Payload 一起保存，命中后可以直接返回正文。此时二者在物理存储上可能位于同一产品中，但逻辑职责仍然不同：Content、来源与版本构成知识资产，Vector Index 是可以根据 Embedding 模型重新生成的派生检索结构。

## 关系不是包含或等同

以下三种情况都成立：

1. **知识库使用向量数据库**：常见的语义检索 RAG。
2. **知识库不使用向量数据库**：使用关键词搜索、SQL、规则或知识图谱查询。
3. **向量数据库不构成知识库**：只保存商品、图片或用户特征向量用于推荐和匹配。

因此更准确的关系是：向量数据库可以是知识库检索层的一部分，而不是知识库本身的同义词。

## 工程上的重要后果

- 原始资料和经过审核的知识记录应被视为事实来源，向量只是可重建的派生索引。
- Content 改变时应检查并刷新受影响的检索表示；删除内容时清理或禁用相关索引。仅权限或过滤字段变化通常只需同步权限与 Metadata，不必重新计算未变文本的 Embedding；检索与取回正文均需遵守权限。
- 更换 Embedding 模型或向量维度时，通常需要重新生成索引，但不等于重建全部原始知识。
- 向量相似度只能产生候选内容，仍需过滤、Rerank、来源检查和生成阶段评估。
- 备份了向量不等于备份了知识；只有 Vector 而没有 Content、来源与版本，难以审计和恢复。
