# RAG应用的构建与落地流程

## 核心认识与课件术语

[[RAG（检索增强生成）]] 解释基本机制，本页回答如何把三个技术环节做成可运行、可评估、可维护的应用。资料更新与索引构建是一条流程；每次提问的检索与生成是另一条；二者需要通过稳定的记录、版本与接口衔接。

课件第 8 页标题为“NativeRAG”，正文是 Indexing → Retrieval → Generation。Gao 等综述在 II-A 节把这类基础形态称为 **Naive RAG**。“Native”是否为讲者笔误只能推测，不能把它当成已确认的另一个标准术语。重排、查询路由等属于常见增强措施，不是每个最简 RAG 都有的必选步骤。

## 从业务目标开始

人先确定应用服务谁、回答哪些问题、哪些来源算依据，以及证据不足时如何处理。业务专家给出代表性问题、正确依据与答案标准；开发者实现处理与服务流程；维护者负责资料同步和运行；这些角色可由同一人承担。

系统目标应可检验：例如不仅要“回答产品问题”，还要正确区分型号、保留“不支持”等否定、引用当前版本、对手册没有的信息说明缺失。具体教学数据与完整 Prompt 见 [[RAG完整案例：从产品手册到有依据的回答]]。

## 三个阶段的输入、工作与输出

| 阶段 | 输入 | 主要工作 | 输出与验收 |
| --- | --- | --- | --- |
| 数据预处理／Indexing | 原始文件、网页或数据库记录 | 选择来源，解析清洗，分块，加来源与权限元数据，编码并建索引 | 可检索记录；正文不遗漏、条件不丢失、能追溯原文 |
| 检索／Retrieval | 问题、必要历史、身份与时间条件 | 补全 Query，选数据源与过滤条件，编码，召回，去重与重排，补全必要上下文 | 当前问题可用的候选证据；不串对象、不混版本、权限合格 |
| 生成／Generation | 原问题、证据、任务指令 | 按预算组装上下文，生成答案与引用，校验结论与输出 | 有依据的回答，或明确的缺失／冲突说明 |

### 一、数据预处理：把资料变成可靠的检索对象

1. **知识准入与维护规则**：确定有效来源、版本、生效时间、适用对象及访问范围；冲突制度不靠相似度分数决定谁正确。知识库管理不等于上传文件，详见 [[RAG知识库的构建策略]]。
2. **解析与清洗**：程序处理 PDF、HTML、OCR 等；人抽查表格、页码、数字、否定和章节关系。扫描件文字、表头和正文顺序错误，会进入后续每一个环节。
3. **分块**：优先按文档结构和独立问题组织，再遵守长度上限。块小可能更聚焦，但会增加记录数并丢失条件；块大保留更多上下文，也可能混入噪声。粒度、重叠、父子关联与回补策略要用真实问题比较，不能仅按字数拍板。详见 [[RAG中的长文档语义切片]]。
4. **元数据与稳定 ID**：记录 `chunk_id`、`document_id`、位置、版本、领域、对象、时间与访问范围，保证向量命中能返回正确正文。派生摘要和合成问题保留到原文的映射，不替代原文。详见 [[向量检索中的ID与元数据]]。
5. **Embedding 与索引**：选适合语言、问题—段落检索和长度要求的模型，按规定编码；保存向量并建立索引。查询侧必须与索引侧兼容。建库通常使用已有编码模型，不等于训练回答用的 LLM。

人负责资料和策略的判断、样本核验与效果标准；程序批量执行；模型可辅助识别结构或编码。人不需要手写每个向量，也不应把所有自动输出直接当成可信内容。

**模型例举的校正**：BGE 是系列名，需明确具体版本；BGE-M3 和 M3E 官方模型卡都说明了文本检索／嵌入用途。Chinese-Alpaca-2 官方项目将它列为指令／Chat 模型，不能直接与专用 Embedding 模型并列。生成模型也可以经过特定适配用于编码，但必须说明表示提取、训练目标和检索评测，不能只因为内部有向量就认为适用。

### 二、检索：从用户表达得到足够的证据

1. 读取原问题与必要历史，解析实体和条件；依赖历史时补全，多个问题可拆分，歧义不足以消解时澄清。改写不能制造用户没有提供的对象、日期或前提。
2. 应用确定可访问的数据源与过滤条件。身份由应用校验；自然语言 Router 不能自行授予权限。可按规则或模型路由，详见 [[RAG中的多知识库组织与路由]]。
3. 按具体检索方式执行召回。向量方案编码 Query，按配置在索引中查候选；关键词、结构化查询或混合检索也可以参与。
4. 合并重复候选并保留来源。查产品型号时需考虑精确字段；向量相似不等于型号、时间、条款一致。
5. 按需要执行 [[检索重排序（Rerank）]]，再检查证据是否覆盖所有子问题，补回父级、邻近条款或另一次检索。仅排序不能补回从未进入候选的证据。

课件“重排序”不能只理解为把向量结果重新按同一个分数排序。显式 Rerank 通常使用额外的相关性判断；是否值得加入，要比较检索质量与延迟。

### 三、生成：组织证据并回答

上下文组装有五类工作：去除冗余、补齐解释所需条件、处理版本与冲突、保留来源标识、分配 Token 预算。不是把所有候选机械拼接；按分数截取也可能把比较问题的一半证据挤掉。

一次模型请求可以概括为：

```text
应用指令 + 必要历史 + 原始问题 + 已核对的证据 + 输出要求
```

检索原文是证据，不是新的应用指令。模型依据它组织答案、比较或推理；应用检查格式、引用存在性及结论是否被材料支持。引用 ID 存在不等于引用确实证明结论，仍需评测或人工核对。只有向量却没取回正文，不能完成常见文本 RAG 的证据注入。

**预算示例（教学假设）**：某请求总预算 1000 Token，指令 120、历史 100、问题 30、来源包装 40、输出预留 80，证据最多剩 `1000−120−100−30−40−80=630`。四段各 220 Token 合计 880，不能全塞。应按任务选择证据、取必要原文范围、压缩重复历史或调整方案；不能截掉关键条件来满足预算。本例仅核算算式，实际限制应使用目标模型与 tokenizer 测量，部分模型另有输出或推理预算规则。

## 从演示到上线增加哪些工作

| 工作 | 为什么需要 | 最小验收问题 |
| --- | --- | --- |
| 版本更新与删除传播 | 新正文、Chunk、派生内容、向量和缓存要一致 | 新版本生效后能否避免旧答案，删除后是否仍可检索？ |
| 失败与异常处理 | OCR、编码、索引写入、检索或生成均可能失败 | 失败文档是否可定位与重试，ID 映射是否仍正确？ |
| 独立评测 | 手写理想问法不能代表真实用户 | 正确证据能否召回，答案是否忠实，无法回答时是否明确？ |
| 性能与资源 | 数据增长、并发和更新会增加负载 | 查询 P95 延迟、吞吐、内存和成本是否达标？ |
| 运行监控与回退 | 上线后会出现新问法、资料冲突和服务故障 | 能否区分没资料、没检到、没用对，能否回到已知可用版本？ |

P95 延迟是 95% 请求不超过的耗时，不能只看平均值。上述是助手整理的工程框架，具体措施按应用需要选择；未在本项目部署。容量与预算详见 [[RAG与向量检索的容量与性能]]，诊断详见 [[RAG的失败诊断与反馈迭代]]。
