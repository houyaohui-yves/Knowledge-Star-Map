# 多Agent与单Agent模块化：区别与选择

## 核心认识

**模块化描述系统怎样拆分职责，多 Agent 描述系统是否包含多个可承担任务和决策的智能体。两者有交集，但不是同义词。** 多 Agent 系统可以采用模块化设计，单个 Agent 也可以包含检索、记忆、计算、工具调度等模块。

本文讨论 LLM Agent 的工程实践，不把下面的观察标准当成所有领域通用的形式定义。不同框架对 Agent 的命名较宽，不能仅凭组件名、角色 Prompt 或模型调用次数判断架构。

## 如何区分

| 观察点 | 单 Agent 加多个模块 | 多 Agent 协作 |
| --- | --- | --- |
| 任务决策 | 主要由一个 Agent 决定后续行动，模块提供能力 | 多个 Agent 在各自职责范围内决定如何完成任务 |
| 下达的内容 | 通常是具体操作及参数 | 可以是子目标、约束和输出要求 |
| 局部执行 | 模块按代码、固定流程或一次模型调用处理 | 子 Agent 可依据结果继续选择行动，直到完成或触及停止条件 |
| 上下文与状态 | 由主 Agent 统一组织，模块也可保存自己的状态 | 常为各 Agent 划分任务上下文，也可共享部分状态 |
| 协作方式 | 函数、工具或子流程调用 | 委派、结果汇总、控制权交接或消息协调 |

其中最有用的判断问题是：**这个组件接到任务后，是否承担局部目标，并能根据反馈决定后续行动？** 这是实用识别方法，不是要求每个 Agent 每次都必须循环多轮。

LangChain 的文档并列讨论子 Agent、交接和单 Agent 按需加载 Skills 等方式，说明相似的职责拆分需求可以有不同实现。子 Agent 也可以通过工具接口暴露；“调用起来像工具”不等于内部没有 Agent。[Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

还应排除几种误判：

- 多个 Agent 可以调用同一个基础模型；模型数量不等于 Agent 数量。
- 单 Agent 可以多次调用模型，甚至使用不同模型处理不同步骤。
- 为“研究员、编辑、检查员”分别写 Prompt，不足以证明存在多个自主决策单元。
- 多 Agent 可以顺序交接；单 Agent 可以并行调用工具。并行不是多 Agent 的定义。
- 独立进程、完全隔离的记忆、不同权限均不是多 Agent 的必要条件；需要这些隔离时，必须由系统实际实现。

## 同一个任务的两种设计

以下为助手教学设计，未实现或测试。任务是比较三个企业 AI 产品。

**单 Agent 模块化方案：** 一个 Agent 负责整个比较任务，调用搜索模块、网页读取模块和表格生成模块。每次工具返回后，由它判断资料是否足够、下一步查什么。即使有十个工具，也可以仍是单 Agent。

**多 Agent 方案：** 协调者将三个产品分别交给三个研究 Agent。每个研究 Agent 在约定范围内自行检索、发现资料缺口、继续追查，再交付带证据的结果，由协调者核对并汇总。

变化的关键是把一部分任务决策委派出去。如果所谓的三个“研究 Agent”实际上只是固定运行一次搜索，再把结果返回，那么将其理解为并行检索模块可能更清楚。

## 如何选择

先做能满足需求的简单方案，再根据实际瓶颈决定是否增加 Agent，是工程启发式，不是“单 Agent 永远更好”。

| 任务特征 | 可优先尝试的方案 | 理由或需验证的条件 |
| --- | --- | --- |
| 步骤清楚，每部分输入输出稳定 | 固定 Workflow 或模块化单 Agent | 容易直接控制和定位错误 |
| 各步骤高度依赖同一段上下文 | 单 Agent，配合上下文管理 | 减少反复传递与同步信息 |
| 可拆成相对独立、需要持续探索的子任务 | 多 Agent | 局部探索可以独立推进并汇总 |
| 专业资料和工具很多，互相干扰 | 先试按需加载、工具筛选；必要时拆 Agent | 需要的是合适的信息边界，不一定是更多 Agent |
| 只是希望代码好维护 | 普通模块化往往足够 | 工程分层不要求引入新的决策单元 |

Anthropic 的研究系统提供了一个实际案例：协调者委派研究任务，子 Agent 在各自上下文中检索并返回结果。其经验显示，适合独立探索的任务能受益，但协调、信息交接和额外计算也有代价；高度依赖共享上下文的任务未必适合这种拆分。[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

选型时，应比较任务正确率、证据覆盖、耗时和成本，并检查是否出现重复调查、任务遗漏或汇总丢失条件。多人式协作不自动产生独立判断：多个 Agent 如果依赖相同错误资料，也可能一致出错。这里是工程分析，不是本项目的实测结论。

## 与 Workflow、ReAct 的关系

这是两个可以组合的观察维度：

- **单／多 Agent：** 谁承担决策，职责分给几个智能体？
- **Workflow／ReAct：** 执行如何组织，后续行动如何确定？

例如，外层 Workflow 先校验输入，再并行调用两个研究 Agent，二者各自使用 ReAct 式的推理—行动—观察循环，最后回到固定的证据检查和汇总步骤。这个教学设计同时包含多 Agent、Workflow 和 ReAct，并不矛盾。

Workflow 是较宽泛的流程编排方式，ReAct 是结合推理和行动的一种具体方法；它们不是同一层级、穷尽所有实现的二选一分类。进一步解释见 [[Agent入门：Workflow、ReAct与平台#三者怎样比较与协作]]。
