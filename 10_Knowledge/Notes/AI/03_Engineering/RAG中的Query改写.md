# RAG中的Query改写

## 核心认识

Query 改写的目标不是让句子更漂亮，也不是替用户改变需求，而是在保留原始意图的前提下，产生一个或多个适合不同检索方式的 Query。原始问题、对话历史和改写结果都应保留，最终回答仍需对齐用户真正提出的问题。

它处理在线请求中的用户意图；知识库的组织与合成问题索引处理离线资料。二者可以配合，但各自维护独立方法。

“双向奔赴”是学习转述中的工程比喻，不是标准学术术语：Query 侧整理表达，知识库侧改善知识单元、索引与元数据。任何一侧都可能成为检索瓶颈，具体是否改善效果需要验证。

## 为什么需要 Query 改写

真实用户很少按照知识库的字段、术语和文档结构提问。他们可能省略主语、使用代词、分多轮追加条件、一次提出多个意图，或者把自然语言条件混在语义问题中。

如果直接把最后一条消息送去检索，系统会丢失前文中的实体、范围与限制条件。Query 改写首先要把当前对话凝结成一个能够脱离历史独立理解的问题，即 Standalone Query；复杂情况下还要进一步拆分、扩展或转换为结构化查询。

还有两种常见错位：用户问的是一个问题，文档用条款或陈述句表达答案；用户在一句话里问几个方面，而候选 Chunk 往往只覆盖其中一个。改写可以对齐表达、补全对象及拆分证据需求。这里的“更适合检索”取决于检索器：向量检索可用完整问题，关键词检索关注实体与术语，结构化检索关注字段与条件，不等于一律写成正式长句。

Embedding 只能编码传给它的内容。在只编码当前 Query 的常见实现中，“那什么时候申报？”并不包含前文的客户经理评聘对象；向量相似度无法可靠地补回没有传入的信息。改写解决的是查询表达与上下文问题，不能补救知识库缺少资料、解析错误或页码映射错误。

问题已经独立、明确时可以原样检索。采用 LLM 改写会增加模型调用，并可能造成意图偏移，收益需要与延迟、费用一起评估，不能默认所有问题都改写。

## 常见 Query 类型与处理方式

以下前五类对应本地课件第 38–42 页；条件型是已有讨论的工程补充。这些标签用于选择操作，不是互斥、穷尽的标准分类。

| 类型 | 主要问题 | 更合适的处理与边界 |
| --- | --- | --- |
| 上下文依赖型 | “保修多久？”依赖前文中的产品 | 补全产品名称、型号与已有条件，改写为可独立理解的问题；只带入相关历史 |
| 对比型 | “哪个保修时间更长？”涉及多个对象和比较维度 | 明确对象及维度；可分别检索各对象的保修期限，再比较。“更好”没有评价标准时需要澄清 |
| 模糊指代型 | “都支持无线充电吗？”中的“都”没有显式对象 | 能唯一确定时换成具体名称；多个对象均可能时先澄清。保留“这些对象是否都支持”的检验意图 |
| 多意图型 | 同时询问颜色、尺码和到货时间 | 拆成带完整对象与条件的子 Query；分解后合并答案。子问题依赖前一步结果时按依赖顺序执行 |
| 反问型 | “投诉一次难道就不扣分吗？”带反问语气 | 在投诉指向明确时检索“客户经理考核办法中，投诉一次是否扣分？适用条件及分值如何规定？”；不把质疑改写成已确定的结论 |
| 条件型 | “有没有不超过 500 元（含 500）、适合某类需求的产品？” | 抽取价格、品类等可校验过滤条件，并保留无法结构化的语义条件；不猜测用户偏好 |

上下文依赖描述“缺少了哪些信息”，指代消解描述“如何补回对象”，二者可以同时存在。比如“它们哪个保修更久？都支持无线充电吗？”需要先消解对象，再按比较维度和多个意图拆分，不能因选中了“多意图型”就跳过指代处理。

此外，还有常见的**词汇不匹配**：用户说“笔记本电脑”，文档写的是“便携式计算机”。在领域词表确认等价时，可以进行术语归一化、同义词扩展或生成多个检索 Query，并保留原表达。

不能把相关概念当成同义词。例如“新员工”不一定处于“试用期”，不能直接替换；如果该区别影响回答，应查明制度的适用对象或向用户澄清。

## Query 改写不只是一句摘要

不同问题需要不同操作：

1. **对话凝结**：汇总多轮历史，生成独立问题。
2. **指代消解**：补回“它、那个、都”等指代的对象。
3. **术语归一化与扩展**：同时保留用户用词和知识库术语。
4. **问题拆分**：把多意图、比较或需要多步证据的问题拆成子 Query。
5. **结构化抽取**：生成字段、操作符和值，用于数据库或元数据过滤。
6. **检索路由配合**：判断应使用向量检索、关键词检索、SQL、API，还是多种方式组合。路由决定去哪里、用什么方式查，改写决定具体查什么；二者可以共用分析结果，但职责不同。

因此，一次改写不必只返回一个“标准 Query”。更稳健的中间结果可以是：

```text
原始问题
独立问题
涉及的实体与属性
多个检索子问题
结构化过滤条件
推荐的检索方式
是否需要向用户澄清
```

例如，用户连续询问两款商品后又说：“哪个保修更久？都支持无线充电吗？”可以拆成：

```text
1. 查询商品 A 的保修期限
2. 查询商品 B 的保修期限
3. 查询商品 A 是否支持无线充电
4. 查询商品 B 是否支持无线充电
```

取回证据后，生成阶段再比较保修期限并汇总无线充电能力。这一步是综合回答任务，不是第五条检索 Query。拆分可以减少只命中其中一个方面的风险，但是否比一个长 Query 更有效，仍需在实际问题和知识库上对照测试。

## 怎样按类型实现改写

一个可落地的流程是：**原始 Query＋相关历史 → 补全对象与条件 → 判断歧义及所需操作 → 生成检索请求 → 校验 → 检索与重排 → 回答原始问题**。信息不足时转入澄清，明确且无需处理时直接检索。

1. **准备输入**：保留当前问题、相关对话、已确认的实体及知识库字段说明。用户最新的明确纠正覆盖旧条件。历史中助手说过的业务信息不自动成为事实，尤其不能把未经证实的答案写进 Query 作为前提。
2. **识别所需操作**：规则适合已知实体替换、受控同义词、明确字段抽取；LLM 适合复杂指代、隐含意图和问题分解。可以用一个 Prompt 同时完成类型识别与改写，也可以先分类再调用专门模板，不必固定为两次模型调用。
3. **组合操作**：允许多标签，优先解决会影响对象与含义的歧义，再拆分、扩展和提取条件。比较问题若有直接比较文档，可保留完整比较 Query；分对象检索是可选策略。
4. **校验输出**：检查对象、否定、数量、时间、比较维度、范围及每个意图是否保留；验证 JSON、字段与枚举是否合法。多个变体命中相同资料时按文档／Chunk ID 去重；每个子问题都要检查证据覆盖，不能只看总召回条数。
5. **接回生成**：Prompt 保留原问题、必要历史及检索证据；改写结果帮助定位资料，不替代原始需求，也不作为事实证据。

可用下面的指令骨架，再加领域内 Few-Shot 样例；这是助手整理的教学模板，未做模型调用测试：

```text
任务：根据当前问题、相关对话和已确认的实体／字段，生成检索请求。
规则：
- 保留原意、否定、数量、时间、范围和比较维度，不回答问题。
- 仅补充输入能支持的信息；历史助手回复中的事实须有依据。
- 先消解对象，再分解意图；每个子问题必须能独立理解。
- 允许多个 query_types；不要只凭“哪个”“不会”等关键词分类。
- 已清楚则 action=passthrough；需改写则 action=rewrite。
- passthrough 时 standalone_query=original_query，queries=[original_query]，
  query_types 和 filters 为空数组；本模板将抽取结构化过滤条件归入 rewrite。
- 存在影响答案且无法消解的歧义则 action=clarify，提出具体澄清问题，
  此时 standalone_query 为空字符串，queries 和 filters 为空数组。
- filters 只能使用提供的字段、操作符和已确认的值；没有则为空数组。
输出合法 JSON，字段：
original_query, action, query_types, standalone_query,
queries（字符串数组）, filters（条件对象数组）, clarification_question。
非澄清分支的 clarification_question 为空字符串。
输入：当前问题、相关对话、已确认实体／字段说明。
```

### 无需改写时的输出示例

假设当前问题是“上海迪士尼乐园停车场收费规则是什么？”，对象与任务已经明确，且本次不需要拆分或抽取结构化条件，可原样交给检索器：

```json
{
  "original_query": "上海迪士尼乐园停车场收费规则是什么？",
  "action": "passthrough",
  "query_types": [],
  "standalone_query": "上海迪士尼乐园停车场收费规则是什么？",
  "queries": ["上海迪士尼乐园停车场收费规则是什么？"],
  "filters": [],
  "clarification_question": ""
}
```

这是助手自拟的教学输出，未调用模型或检索服务。`passthrough` 表示保留查询原文，不表示已经知道答案；下游仍需检索收费资料。若问题需要补全、拆分或提取过滤条件则用 `rewrite`；影响答案的歧义无法消解时用 `clarify`，等待用户补充后再生成检索请求。

### 沿用客户经理 PDF 案例的最小示例

假设对话中用户已说明“我在看客户经理考核办法，想了解评聘流程”，接着问“那什么时候申报？考试呢？”。可产生：

```json
{
  "original_query": "那什么时候申报？考试呢？",
  "action": "rewrite",
  "query_types": ["上下文依赖型", "多意图型"],
  "standalone_query": "客户经理考核办法中，评聘申报和评聘考试分别在什么时间进行？",
  "queries": [
    "客户经理考核办法中，评聘申报在什么时间进行？",
    "客户经理考核办法中，评聘考试在什么时间进行？"
  ],
  "filters": [],
  "clarification_question": ""
}
```

改写器此时不填写申报或考试月份，月份应从真实制度中取回。随后用与索引兼容的 Embedding 配置编码两个子 Query，分别召回、必要时重排，合并去重后交给生成模型回答两问。真实 PDF 与 demo 的基础链路见 [[客户经理考核PDF问答案例：从文档到回答与页码溯源]]；本例是新增的教学设定，未接入或改动 demo。

如果前文同时讨论投诉扣分与其他扣分事项，当前只有“那扣几分？”，且不能确定所指，就应澄清“你问的是投诉扣分，还是刚才提到的另一项扣分？”；不能凭改写模型猜一个分值或事项。

## 对照课件检查改写质量

第 37 页以“翻译官”解释口语问题与知识库表达之间的差距，第 38–42 页分别给出专门 Prompt，第 43–44 页尝试类型识别与统一输出。这个思路可作为起点，但分类标签不保证改写成功：

- 第 44 页的“之前提到的”“这”仍依赖历史，未形成独立 Query。
- “都适合小朋友吗？”询问已知对象是否全部满足条件；改成“哪些产品或活动适合小朋友？”变为开放推荐，改变了范围与任务。
- “哪个园区更好玩？（请明确是哪些园区）”属于澄清请求，应交给用户，而不是直接拿去检索。若评价维度不清楚，还需要明确用户关注什么。
- 第 41 页要求 JSON 数组，展示结果用单引号，是 Python 列表形式。结合 demo 可见，合法 JSON 经 `json.loads` 后打印列表也会呈现这种形式，不能只凭截图断定模型解析失败；但“门票多少钱”等子问题仍没有补出对象。应用需要分别检查原始响应格式、解析后的结构与语义完整性。
- 第 42 页的中性化示例没有保留前文的“上海”和目标游玩日；这些条件若决定票务规则，就不应随反问语气一起被删掉。
- 第 38–40 页的历史助手回复只作为课件输入，其设施与活动信息未核验；改写时不能把这类回复升级为真实业务事实。

第 43 页用关键词描述分类并设定“多意图优先于模糊指代”，不是通用处理顺序；“不会使用这个功能，怎么办？”里的“不会”也不一定是反问。第 44 页反复输出的 `0.95` 是模型自报值，未做校准，不能当作正确率或允许猜测的依据。

## 假设文档作为检索表示

除了补全实体、同义词、条件及拆分子问题，还可以生成更接近文档措辞的检索语句，或一段“假设性的答案或知识段落”，再编码为向量检索真实文档。

后一种方式通常称为 Hypothetical Document Embeddings（HyDE）思路：模型不需要先知道真实答案，而是生成一段在表达形式上像答案的假设文档，用它跨越“问题—文档”之间的表达差异。

假设内容可能包含错误，因此它只能作为检索入口，不能作为最终事实依据。最终答案仍应以真实召回的权威 Chunk 为依据。

## 条件查询与 SQL 的安全边界

条件型 Query 可以转成 SQL，但不宜让 LLM 直接生成并执行任意 SQL。更可靠的方式是让模型先输出受约束的结构化条件。例如，前文“不超过 500 元（含 500）”对应的价格条件是：

```text
category = 指定品类
price <= 500
required_features = [...]
```

如果用户明确说“低于 500 元（不含 500）”，则对应 `price < 500`。用 499、500、501 元检查边界：“不超过 500 元”保留 499 和 500，“低于 500 元”只保留 499，两者都排除 501。自然语言没有明确是否包含边界且该区别影响结果时，应确认含义，不能机械套用运算符。

应用再校验字段、类型和操作符，通过参数化查询或受控 Query Builder 生成只读 SQL。对于“适合女生”这类主观条件，只有知识库存在经过定义的对应属性时才能用于过滤；否则应改写成可验证的需求，例如尺寸、重量、颜色偏好或使用场景，必要时向用户追问，而不是根据性别刻板印象擅自筛选。

## 用改写样例教模型

把历史 Query 与期望改写结果整理成高质量输入—输出对，可以通过 Few-Shot 告诉模型如何处理不同问题。样例应覆盖：

- 不同的 Query 类型和业务领域；
- 应当拆分、扩展或转为结构化条件的情况；
- 信息不足、必须澄清而不能猜测的情况；
- 表达已经清楚、不需要改写的情况。

样例较多时，可按 [[动态Few-Shot样例选择]] 的流程选择改写示范。这里的输入—输出对属于 [[Few-Shot提示]]，示范的是“怎样改写”，不是提供回答所需的事实知识。

## 主要风险与评估

Query 改写可能带来新的错误：

- 遗漏用户在前文给出的限制条件；
- 把模糊指代错误绑定到某个实体；
- 擅自添加用户没有表达的条件；
- 过度概括，导致多意图问题只剩下一个意图；
- 丢失否定或量词，把“是否都满足”变成“有哪些满足”；
- 将历史助手的错误信息固化为查询前提；
- 生成合法但语义错误或越权的数据库查询。

因此应同时评估两件事：

1. **语义保真**：改写是否完整保留了用户意图，没有添加未经确认的信息。
2. **检索收益**：正确证据进入 Top-K 的比例是否真的提高，最终答案是否改善。

不能只凭改写文本“读起来更专业”判断效果。真实失败问题、原始 Query、改写结果、召回内容与最终答案应一起进入评测记录。

对照实验应固定文档、索引、检索／重排参数及生成配置，比较原始 Query 与改写方案；按类型观察证据 Recall@K、多意图证据覆盖、最终答案完整性及延迟／费用。对歧义问题，正确发起澄清也是成功处理，不能为了提高改写比例而猜测对象。本文没有这类实验结果。

## 知识库侧如何配合

Query 侧整理用户意图，知识库侧按任务组织内容、保留原文依据并改善检索表示。两侧需要使用相容的实体、条件与任务粒度，但不要在 Query 改写笔记中重复维护知识库设计。
