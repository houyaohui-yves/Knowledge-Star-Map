# RAG的失败诊断与反馈迭代

## 核心认识

RAG 排错首先要区分资料有没有、证据是否被找到、答案是否忠于证据。用户反馈和低相似度分数可以提示异常，却不能单独确定根因；修复应有原文、检索轨迹和对照结果支持。

## 从真实问题建立反馈闭环

生产环境中的真实问题是改进 RAG 的重要材料。以下信号值得单独收集：

- 没有召回任何内容；
- 召回内容的分数或相关性较低；
- 召回内容看似相关，却不足以回答问题；
- 已召回正确证据，但最终答案仍然错误；
- 用户纠正、追问、放弃或给出负面反馈。

但“没有结果”或“相关度低”只是异常信号，不能直接证明知识库中缺少知识。

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 没有召回结果 | 知识确实缺失；解析失败；过滤条件过严；查询与文档用词不同 | 原始资料是否包含答案、解析结果、过滤器、查询改写 |
| 召回分数低 | 知识缺失；Chunk 表达不完整；嵌入模型不适合；语义与关键词不匹配 | Chunk、Embedding、混合检索、阈值 |
| 高分结果不相关 | 向量相似产生误召回；Chunk 混入多个主题 | 切片策略、元数据过滤、Rerank |
| 正确证据未进入 Top-K | 召回或排序失败 | Top-K、关键词召回、查询扩展、Rerank |
| 正确证据已召回但回答错误 | Prompt、上下文组织或生成阶段失败 | 提示词、证据顺序、输出约束、模型 |

相似度分数还依赖嵌入模型、距离度量和数据分布，不能把一个固定阈值直接套用到所有知识库。

## 迭代流程

一个可操作的闭环是：

```text
记录真实查询与检索轨迹
→ 标注预期答案和应命中的证据
→ 判断失败发生在哪一层
→ 修复资料、切片、索引、检索或生成流程
→ 把该问题加入评测集
→ 回归测试，确认修复没有破坏其他问题
```

每条问题至少应记录：原始 Query、查询改写、召回的 Chunk 与分数、最终答案、引用来源、用户反馈和处理结果。这样才能区分“知识覆盖不足”“知识存在但没找到”和“找到证据却没答对”。

积累下来的真实问题不应只用于补知识，也应成为稳定的评测集。每次更换 Chunk 策略、嵌入模型、检索器、Reranker 或 Prompt 后，都应重新运行这些问题，比较修改前后的表现。

## 一个企业制度问答例子

用户问：“试用期员工请三天病假是否影响转正？”系统没有召回内容时，应依次检查：

1. 原始制度中是否真的规定了试用期、病假与转正之间的关系；
2. PDF 是否正确解析，相关表格或脚注是否丢失；
3. 相关规定是否因切片而分散在不同 Chunk；
4. 查询与制度的术语是否不匹配；“试用期员工”与“新入职人员”不能自动当成同义词，应核对各自适用范围；
5. 过滤器是否排除了正确版本；
6. 如果知识确实不存在，再请业务负责人补充权威规则或明确系统应回答“不知道”。

这个过程避免把所有失败都错误归因于“知识不够多”。
