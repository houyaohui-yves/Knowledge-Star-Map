# RAG 中的 Query 与知识切片语义对齐

## 核心认识

用户通常用问题表达需求，知识库通常保存陈述事实的文档段落。二者在措辞、长度和表达结构上不同，形成 Query–Document 语义鸿沟。RAG 可以从两侧缩小差距：

- **Query 侧**：把问题扩展为关键词、知识点、子问题或一段可能的答案，再进行检索。
- **知识库侧**：为每个知识切片生成用户可能提出的典型问题，让真实 Query 可以与这些问题进行匹配。

不过，“问题与长段落的向量相似度一定很低”并非普遍规律。面向检索训练的 Embedding 模型通常能够处理 Query–Passage 这种非对称匹配，有些模型还要求分别添加 query 与 passage 前缀。两侧改写属于进一步优化，是否有效必须用真实问题的召回结果验证。

## 方法一：把 Query 改写成知识表达

用户的问题可以产生一种或多种检索表示：

- 提取核心实体、主题、同义词和限定条件；
- 把多意图问题拆成多个知识点或子 Query；
- 生成更接近文档措辞的检索语句；
- 生成一段“假设性的答案或知识段落”，再用它的向量检索真实文档。

最后一种方式通常称为 Hypothetical Document Embeddings（HyDE）思路：模型不需要先知道真实答案，而是生成一段在表达形式上像答案的假设文档，用它跨越“问题—文档”之间的表达差异。

假设内容可能包含错误，因此它只能作为检索入口，不能作为最终事实依据。最终答案仍应以真实召回的权威 Chunk 为依据。

## 方法二：为知识切片生成典型问题

建库时，可以让模型阅读每个 Chunk，生成若干能够由该 Chunk 回答的典型问题，形成 `question-content` 映射：

```text
question 1 ─┐
question 2 ─┼─→ 原始 content / Chunk
question 3 ─┘
```

检索时，用户 Query 与合成问题在表达形式上更接近。命中某个 question 后，系统返回与它关联的原始 content，供后续 Rerank 和生成使用。这里采用的是合成问题索引；一个 Chunk 对应多个检索向量时，也属于广义多向量检索的一种实现。

它与 doc2query 都借助预测问题扩展文档的检索入口，但不能视为同一实现：原始 doc2query 将预测查询用于扩展文档，本文则单独索引问题向量并映射回 Content；也不要把这种父子映射与特定数据库的 MultiVector 数据类型直接等同。

更精确地说，运行时通常不会把用户 Query 作为新记录存入向量数据库，而是临时生成 Query Vector，用它搜索已经存储的 Question Vector。检索结果通过 `chunk_id` 等映射取回 Content：

```text
用户 Query
→ 临时生成 Query Vector
→ 匹配已存储的 Question Vector
→ 根据映射取回原始 Content
→ 将 Content 放入最终 Prompt
```

这与动态 Few-Shot 不同：这里生成的 question 默认只是检索键，通常不需要放入最终 Prompt；真正作为回答证据进入 Prompt 的是它所指向的原始 content。只有当问答对被明确作为任务示范使用时，它才承担 Few-Shot 样例的角色。

较合适的数据结构是：

```text
chunk_id
content
source / version / location
metadata
synthetic_questions:
  - question_text
  - question_vector
```

不一定要把所有 question 与 content 拼成一段长文本后只生成一个向量。将问题向量作为独立检索入口，并共同指向父级 Chunk，通常更方便控制、去重和分析究竟是哪一种问法产生了命中。

## 如何生成高质量问题

生成提示词不应只要求“根据这段内容提几个问题”，还应约束：

- 每个问题必须能够仅依据当前 Chunk 回答；
- 不得加入 Chunk 中没有的实体、条件或结论；
- 覆盖不同用户措辞、术语别名和问题粒度；
- 覆盖事实、条件、例外、时间或流程等真正重要的信息；
- 避免只替换几个词的重复问题；
- 无法独立回答的 Chunk 不应强行生成完整问答。

例如，以下是虚构组织的教学规则，仅用于演示问题生成，不是现实劳动法规或任何公司的制度：

```text
正式员工连续工作满一年后享有五天年假；试用期员工不适用该规则。
```

可以生成：

```text
员工工作满一年有几天年假？
试用期员工能否享受五天年假？
五天年假的适用条件是什么？
```

这些问题必须都映射回原始 Chunk。生成的问题只是检索入口，原文才是回答依据。

## 扩展已有 FAQ 或客服 SOP

原本已经是“一问一答”的知识库，也可能只有一个标准 Question，无法覆盖用户的口语、简称、不同句式和隐含条件。可以保留标准问题与标准答案，再让模型根据 Answer 生成多个能够由它回答的关联 Question：

```text
canonical_question ─┐
synthetic_question 1 ├─→ answer_id → content
synthetic_question 2 ┤
real_user_question  ─┘
```

扩写应追求覆盖不同的真实表达，而不是机械地增加同义句数量。可以覆盖：

- 正式表达、口语表达、简称和常见业务术语；
- 不同句式；独立问题应保留必要实体与条件，不能把“多久？”这类无主语短句直接作为跨产品的通用索引键。确需短问法时，应有明确的会话实体和元数据范围；
- Answer 中明确存在的条件、例外、时间、对象和操作步骤；
- 用户从不同任务阶段或关注点提出的同一意图。

更多 Question 会增加某条 Content 被召回的入口，通常有机会提高召回率，但数量并非越多越好。过多的低质量或含义相近的问题会扩大索引、增加重复命中，也可能让该 Content 在无关 Query 下被误召回，从而损害准确率。

“每条生成 5～20 个问题”可以作为实验起点，不是通用规则。数量不应只由 Answer 的文字长度决定，更应该由其中包含多少个能够独立回答的事实、意图、条件和例外决定：

- 内容简单、意图单一时，只需少量具有明显表达差异的问题；
- 内容较长但仍是同一意图时，应控制数量并进行语义去重；
- 内容包含多个独立意图时，应优先把 Content 拆成较原子的知识单元，再分别生成问题，而不是把更多问题都映射到同一条宽泛答案。

合成后还应检查每个问题能否由对应 Content 独立回答，删除重复、含义漂移和引入新事实的问题。上线后，经过验证的真实用户 Query 应逐渐补充或替换纯合成问法，并记录 Question 是标准问题、AI 合成还是来自真实用户，以便分析效果与维护来源。

## 两侧方法可以组合

更完整的召回流程可以同时保留多条路径：

```text
原始 Query ─────────→ 原始 Chunk 索引
原始 Query ─────────→ 合成问题索引 ─→ 父级 Chunk
改写 Query / 知识点 ─→ 原始 Chunk 索引
假设答案向量 ───────→ 原始 Chunk 索引
                       ↓
                合并、去重与 Rerank
```

这样不会把系统成败押在单一改写方法上。关键词检索和元数据过滤仍可以同时参与，最后对多路候选做融合、去重与重排。

## 风险与评估

- 合成问题可能覆盖不全，使系统只擅长回答模型预想过的问题。
- 模型可能生成无法由原文回答的问题，造成错误索引。
- 多个问题向量会增加索引规模、建库成本和维护复杂度。
- 原始 Chunk 更新后，关联的合成问题也需要重新生成或重新审核。
- Query 改写和合成问题可能同时引入偏差，使错误匹配看起来很合理。

因此应保留一组没有参与问题生成的真实用户 Query，用它比较不同方案下正确 Chunk 的 Recall@K、排序位置和最终答案效果。只有指标和错误案例确实改善，才能说明问题生成带来了收益。
