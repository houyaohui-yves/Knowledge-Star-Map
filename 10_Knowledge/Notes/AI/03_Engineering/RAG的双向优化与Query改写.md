# RAG 的双向优化与 Query 改写

## 核心认识

“双向奔赴”不是 RAG 的标准学术术语，而是一种实用的工程比喻：

- **Query 侧**：把用户自然、零散或含糊的表达，转成更适合检索的表示。
- **知识库侧**：把原始资料加工成更贴近用户问题的知识单元、索引和元数据。

两侧共同优化，可以缩小“用户怎样提问”与“知识怎样被保存”之间的表达差距。只优化一侧，另一侧仍可能成为检索瓶颈。

Query 改写的目标不是让句子更漂亮，也不是替用户改变需求，而是在保留原始意图的前提下，产生一个或多个适合不同检索方式的 Query。原始问题、对话历史和改写结果都应保留，最终回答仍需对齐用户真正提出的问题。

## 为什么需要 Query 改写

真实用户很少按照知识库的字段、术语和文档结构提问。他们可能省略主语、使用代词、分多轮追加条件、一次提出多个意图，或者把自然语言条件混在语义问题中。

如果直接把最后一条消息送去检索，系统会丢失前文中的实体、范围与限制条件。Query 改写首先要把当前对话凝结成一个能够脱离历史独立理解的问题，即 Standalone Query；复杂情况下还要进一步拆分、扩展或转换为结构化查询。

## 常见 Query 类型与处理方式

| 类型 | 主要问题 | 更合适的处理 |
| --- | --- | --- |
| 上下文依赖型 | “保修多久？”依赖前文中的产品 | 补全实体与已有条件，改写为可独立理解的问题 |
| 对比型 | “哪个保修时间更长？”涉及多个对象和比较维度 | 明确比较对象与维度；分别检索各对象，再汇总比较 |
| 模糊指代型 | “都支持无线充电吗？”中的“都”没有显式对象 | 做指代消解；存在多种解释时向用户澄清，不能强行猜测 |
| 多意图型 | 同时询问颜色、尺码和到货时间 | 拆成多个子 Query，分别检索后合并答案 |
| 条件型 | “有没有 500 元以下、适合某类需求的产品？” | 抽取价格、品类等结构化过滤条件，并保留无法结构化的语义条件 |

此外，还有常见的**词汇不匹配**：用户说“笔记本电脑”，文档写的是“便携式计算机”。在领域词表确认等价时，可以进行术语归一化、同义词扩展或生成多个检索 Query，并保留原表达。

不能把相关概念当成同义词。例如“新员工”不一定处于“试用期”，不能直接替换；如果该区别影响回答，应查明制度的适用对象或向用户澄清。

## Query 改写不只是一句摘要

不同问题需要不同操作：

1. **对话凝结**：汇总多轮历史，生成独立问题。
2. **指代消解**：补回“它、那个、都”等指代的对象。
3. **术语归一化与扩展**：同时保留用户用词和知识库术语。
4. **问题拆分**：把多意图、比较或需要多步证据的问题拆成子 Query。
5. **结构化抽取**：生成字段、操作符和值，用于数据库或元数据过滤。
6. **检索路由**：判断应使用向量检索、关键词检索、SQL、API，还是多种方式组合。

因此，一次改写不必只返回一个“标准 Query”。更稳健的中间结果可以是：

```text
原始问题
独立问题
涉及的实体与属性
多个检索子问题
结构化过滤条件
推荐的检索方式
是否需要向用户澄清
```

例如，用户连续询问两款商品后又说：“哪个保修更久？都支持无线充电吗？”可以拆成：

```text
1. 查询商品 A 的保修期限
2. 查询商品 B 的保修期限
3. 查询商品 A 是否支持无线充电
4. 查询商品 B 是否支持无线充电
5. 根据检索结果比较保修期限并汇总无线充电能力
```

这样通常比生成一个包含所有条件的长向量 Query 更容易获得完整证据。

## 条件查询与 SQL 的安全边界

条件型 Query 可以转成 SQL，但不宜让 LLM 直接生成并执行任意 SQL。更可靠的方式是让模型先输出受约束的结构化条件，例如：

```text
category = 指定品类
price < 500
required_features = [...]
```

应用再校验字段、类型和操作符，通过参数化查询或受控 Query Builder 生成只读 SQL。对于“适合女生”这类主观条件，只有知识库存在经过定义的对应属性时才能用于过滤；否则应改写成可验证的需求，例如尺寸、重量、颜色偏好或使用场景，必要时向用户追问，而不是根据性别刻板印象擅自筛选。

## 用改写样例教模型

把历史 Query 与期望改写结果整理成高质量输入—输出对，可以通过 Few-Shot 告诉模型如何处理不同问题。样例应覆盖：

- 不同的 Query 类型和业务领域；
- 应当拆分、扩展或转为结构化条件的情况；
- 信息不足、必须澄清而不能猜测的情况；
- 表达已经清楚、不需要改写的情况。

样例较多时，可以先根据当前 Query 动态检索相似的改写样例，再放入 Prompt。这里检索的是“怎样改写”的示范，而不是回答用户所需的事实知识。

## 主要风险与评估

Query 改写可能带来新的错误：

- 遗漏用户在前文给出的限制条件；
- 把模糊指代错误绑定到某个实体；
- 擅自添加用户没有表达的条件；
- 过度概括，导致多意图问题只剩下一个意图；
- 生成合法但语义错误或越权的数据库查询。

因此应同时评估两件事：

1. **语义保真**：改写是否完整保留了用户意图，没有添加未经确认的信息。
2. **检索收益**：正确证据进入 Top-K 的比例是否真的提高，最终答案是否改善。

不能只凭改写文本“读起来更专业”判断效果。真实失败问题、原始 Query、改写结果、召回内容与最终答案应一起进入评测记录。

## 知识库侧如何配合

Query 侧归一化用户表达的同时，知识库侧也可以利用真实提问持续增加常用别名、用户语言表述、结构化元数据、面向问题的摘要和问答知识，并改善 Chunk 的主题完整性。双方使用相近的实体、术语和任务粒度，才是“双向奔赴”的核心。

### 先理解目标问题空间

知识库处理不能只从“手里有哪些文件”出发，还要从“用户需要完成什么任务”反推知识应该怎样组织。上线前应通过用户访谈、客服记录、站内搜索词、历史工单和业务专家整理，建立初始的问题分类与典型问法。

“完全清楚用户都会问什么、都会怎么问”是理想目标，但真实环境无法在上线前穷尽。更可行的做法是：

1. 明确系统要覆盖和不覆盖的任务边界；
2. 为主要问题类型收集代表性 Query，而不是只写一种标准问法；
3. 标注每类问题需要哪些事实、条件、关系和输出形式；
4. 把这些问题作为初始评测集；
5. 上线后持续用真实 Query 和失败案例扩展问题空间。

需要理解的不只是用户使用的词语，还包括其真实意图、涉及的实体与条件、需要几步证据、答案时效性，以及什么来源才具有权威性。

### 按问题类型设计知识表示

不同问题需要的知识结构和检索方式可能不同：

| 问题类型 | 知识处理方向 | 常见检索方式 |
| --- | --- | --- |
| 直接事实型 | 形成主题单一、能够独立理解的 Chunk，保留名称、别名、来源和时间 | 关键词与向量混合检索 |
| 制度或条件型 | 显式整理适用对象、前置条件、例外、生效日期和规则优先级 | 元数据过滤、规则、SQL 与文本证据结合 |
| 对比型 | 让不同对象使用统一字段和属性口径 | 分别检索对象或查询结构化数据后比较 |
| 多意图型 | 将知识按可独立回答的意图组织，并保存清楚的主题标签 | Query 拆分、分路召回后合并 |
| 流程型 | 保留步骤顺序、前置条件、分支、异常和完成标准 | 结构化步骤、章节或父子 Chunk 检索 |
| 跨文档或多跳型 | 显式维护实体关系、文档连接和父子层级 | 多阶段检索、图关系或层级检索 |
| FAQ 型 | 保存常见问法、标准答案及其权威依据 | 问题匹配与事实证据共同召回 |
| 任务示范型 | 保存输入、理想输出、适用范围和质量标签 | 动态 Few-Shot 样例检索 |

这些类型不必各自建立一个物理数据库。它们可以使用不同数据库，也可以共存在同一存储的逻辑分区、不同索引或不同集合中，由 Query 分类器或 Router 选择合适的知识源与检索器。重点不是“分几个库”，而是避免用同一种 Chunk 和同一种向量检索强行解决所有问题。

### 知识改写的原则

面向用户问题重新组织知识时，应同时保留两层内容：

- **原始事实层**：权威文件、原文片段、版本和来源位置；
- **派生知识层**：主题摘要、问答、统一字段、用户语言别名和任务样例。

派生内容用于提高检索和生成效果，但不能失去到原始事实的映射。否则知识改写可能把限制条件删掉、把解释写成事实，或在原文件更新后继续返回过期答案。

知识库也不应只围绕已经收集到的标准问题过度拟合。需要保留未见问法、边界条件和无法回答案例，用评测确认系统既能命中已知问题，也能在证据不足时明确拒答或请求澄清。

针对 Query 是问题、Chunk 是陈述性段落所产生的表达差异，可以在 Query 侧生成知识点或假设答案，也可以在知识库侧为 Chunk 生成多个典型问题并建立问题索引。具体方法见 [[RAG中的Query与知识切片语义对齐]]。
