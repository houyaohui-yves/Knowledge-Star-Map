# RAG 知识库的构建策略与反馈迭代

## 核心认识

RAG 知识库可以采用“直接索引原始文档”“人工整理知识单元”和“检索高质量问答或任务样例”等策略。它们的加工与维护成本不同，不是行业统一的三级分类，也不是必须依次升级的成熟度路线。

实际系统往往组合使用：原始文档保存事实依据，人工知识单元提高检索精度，问答或任务样例帮助模型理解如何回答。选择哪种策略取决于任务复杂度、准确性要求、资料变化速度和人工维护成本。

## 策略一：直接索引原始文档

收集企业制度、产品手册等文件，完成解析、常规切片、元数据补充和索引后直接用于检索。

它适合以下情况：

- 文档质量较高、结构清楚且内容相对稳定；
- 用户问题通常能在某个局部段落中直接找到答案；
- 当前目标是快速上线并覆盖基础问答。

“不用额外处理”不等于完全不处理。至少仍需确保文字解析正确、切片没有破坏语义、来源可以追溯，并清理重复或失效版本。表格、扫描件、跨章节条件和多份制度冲突时，简单切片容易失效。

## 策略二：整理面向主题的知识单元

在原始文件基础上，按独立主题、业务对象或用户任务重新组织 Chunk。例如把分散在多处的适用对象、办理条件、例外情况和生效日期整理成一个能够独立理解的知识单元。

这种方式可能提高召回与回答质量，因为一个 Chunk 更接近用户真正提出的问题。但它也带来人工成本和新的风险：

- 整理者可能遗漏限制条件或改变原意；
- 派生知识可能随着源文件更新而过期；
- 人工整理不能代替检索评测，整理得更多不等于效果必然更好。

因此，人工知识单元应保留到原始文件、版本、页码或条款的映射，并建立随源资料更新的维护机制。

## 策略三：问答知识与动态样例

把真实问题和高质量答案整理成结构化问答，可以有两种不同用途：

1. **FAQ 式知识检索**：检索到“问题—标准答案”，把标准答案作为回答依据。
2. **动态 Few-Shot**：检索到“输入—理想输出”样例，把它作为 Prompt 中的示范，告诉模型应该怎样完成任务。

二者不能混为一谈。前者主要提供“回答什么”，后者主要示范“怎样回答”。一个问答条目也可能同时包含事实依据和表达示范，但系统设计时仍应明确它扮演的角色。

动态样例尤其适合分类、信息抽取、固定格式生成或有明确判断边界的任务。它不天然比文档 RAG 更高级，也不能替代事实来源：样例覆盖有限、整理成本高，还可能因业务规则变化而失效。

一种常见组合是：

```text
事实知识库 → 检索回答所需的证据
样例库     → 检索完成任务所需的示范
二者共同进入 Prompt → LLM 生成答案
```

## 从真实问题建立反馈闭环

生产环境中的真实问题是改进 RAG 的重要材料。以下信号值得单独收集：

- 没有召回任何内容；
- 召回内容的分数或相关性较低；
- 召回内容看似相关，却不足以回答问题；
- 已召回正确证据，但最终答案仍然错误；
- 用户纠正、追问、放弃或给出负面反馈。

但“没有结果”或“相关度低”只是异常信号，不能直接证明知识库中缺少知识。

| 现象 | 可能原因 | 优先检查 |
| --- | --- | --- |
| 没有召回结果 | 知识确实缺失；解析失败；过滤条件过严；查询与文档用词不同 | 原始资料是否包含答案、解析结果、过滤器、查询改写 |
| 召回分数低 | 知识缺失；Chunk 表达不完整；嵌入模型不适合；语义与关键词不匹配 | Chunk、Embedding、混合检索、阈值 |
| 高分结果不相关 | 向量相似产生误召回；Chunk 混入多个主题 | 切片策略、元数据过滤、Rerank |
| 正确证据未进入 Top-K | 召回或排序失败 | Top-K、关键词召回、查询扩展、Rerank |
| 正确证据已召回但回答错误 | Prompt、上下文组织或生成阶段失败 | 提示词、证据顺序、输出约束、模型 |

相似度分数还依赖嵌入模型、距离度量和数据分布，不能把一个固定阈值直接套用到所有知识库。

## 迭代流程

一个可操作的闭环是：

```text
记录真实查询与检索轨迹
→ 标注预期答案和应命中的证据
→ 判断失败发生在哪一层
→ 修复资料、切片、索引、检索或生成流程
→ 把该问题加入评测集
→ 回归测试，确认修复没有破坏其他问题
```

每条问题至少应记录：原始 Query、查询改写、召回的 Chunk 与分数、最终答案、引用来源、用户反馈和处理结果。这样才能区分“知识覆盖不足”“知识存在但没找到”和“找到证据却没答对”。

积累下来的真实问题不应只用于补知识，也应成为稳定的评测集。每次更换 Chunk 策略、嵌入模型、检索器、Reranker 或 Prompt 后，都应重新运行这些问题，比较修改前后的表现。

## 一个企业制度问答例子

用户问：“试用期员工请三天病假是否影响转正？”系统没有召回内容时，应依次检查：

1. 原始制度中是否真的规定了试用期、病假与转正之间的关系；
2. PDF 是否正确解析，相关表格或脚注是否丢失；
3. 相关规定是否因切片而分散在不同 Chunk；
4. 查询与制度的术语是否不匹配；“试用期员工”与“新入职人员”不能自动当成同义词，应核对各自适用范围；
5. 过滤器是否排除了正确版本；
6. 如果知识确实不存在，再请业务负责人补充权威规则或明确系统应回答“不知道”。

这个过程避免把所有失败都错误归因于“知识不够多”。
