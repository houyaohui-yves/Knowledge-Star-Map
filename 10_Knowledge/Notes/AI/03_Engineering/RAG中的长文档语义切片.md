# RAG 中的长文档语义切片

## 核心认识

> 本文是对用户提出的逐段切片思路的工程化建议，尚未在五万字会议原稿上实现或评测，不是已证实优于其他方案的算法。

长文档可以由 LLM 帮助识别主题边界，但切片仍需要程序控制长度、位置和完整覆盖。一个稳健的目标是：优先在语义边界切分，同时遵守检索与上下文所允许的硬上限。

“设定一个字数上限，并保证同一主题绝不被切断”无法同时绝对满足。一个主题本身可能超过上限，此时应把它拆成属于同一父主题的多个连续子 Chunk，并保留父主题、相邻关系和必要上下文。

长度最好按 Token 而不是字符衡量。字符数可以用于粗略估算，但 Embedding 模型和 LLM 的限制、成本及上下文窗口最终按 Token 计算。

## 会议记录的预处理

对于五万字会议记录，先把原稿转换成稳定的最小单元，例如句子或发言轮次，并为每个单元分配不可变 ID：

```text
U0001 | 00:01:15 | 张三 | ……
U0002 | 00:01:42 | 李四 | ……
U0003 | 00:02:10 | 张三 | ……
```

预处理应尽量保留：

- 发言人、时间戳和会议议程；
- 决策、行动项、负责人和截止时间；
- 标题、列表及上下文关系；
- 原始文档 ID、版本和位置范围。

自动语音识别产生的乱码、重复口头语可以清理，但不能在没有核对的情况下改变结论、责任人或数字。会议内容还可能包含敏感信息，发送给外部模型前应确认权限、脱敏要求和数据处理范围。

## 一种可选的两级切片

### 第一级：粗粒度主题分段

先根据议程、显式标题、长停顿、话题转换和会议结构，把全文划分成较大的主题段落。每个主题段保留标题、摘要和覆盖的单元 ID 范围。

### 第二级：主题内子 Chunk

如果某个主题段仍超过检索所需的最大 Token 数，则在该主题内部继续按自然边界拆分。多个子 Chunk 共享同一个 `parent_topic_id`，并记录前后相邻关系。检索时可以先命中子 Chunk，再按需要补回父级摘要或相邻内容。

```text
会议
└── 主题：第三季度预算
    ├── Chunk A：预算目标与限制
    ├── Chunk B：部门预算讨论
    └── Chunk C：最终决议与行动项
```

这种父子结构比强行让一个完整主题全部进入一个超大 Chunk 更适合检索。

## 用 LLM 迭代寻找边界

用户提出的逐段算法是可行的，但应让模型选择“单元 ID 之间的边界”，而不是返回第几个字符。字符计数可能因标点、Unicode、换行或模型复述文本而错位。

一个更稳健的流程是：

1. 设置目标长度、软上限和硬上限，均使用 Token 估算。
2. 从当前游标开始，取一组带 ID 的句子或发言轮次，并附带少量前文摘要和向后 Lookahead。
3. 让 LLM 判断第一个主题是否结束，并返回最后一个属于该主题的单元 ID、主题标题、是否仍在延续及置信度。
4. 程序校验返回 ID 必须存在、边界必须向前推进、Chunk 不能超过硬上限。
5. 按原文 ID 截取，不让 LLM 重写正文；随后把游标移动到下一个单元。
6. 如果窗口内没有自然边界，在硬上限前选择最近的句子或发言轮次边界，并标记 `continued: true`。
7. 重复直到全文处理完毕，再验证是否有遗漏、重复或顺序错乱。

实现时还需处理边界情况：到达文末后保存剩余单元；无自然边界且仍有预算时可先扩窗；单条发言已超过硬上限时先细分并保留父 ID。无效或不前进的边界 ID 应有限重试，再回退到确定性切分并标记待复核，不能无限循环或丢弃正文。

可以要求模型返回受约束的结构：

```json
{
  "topic": "第三季度预算限制",
  "end_unit_id": "U0148",
  "continued": false,
  "boundary_reason": "下一发言开始讨论人员招聘"
}
```

代码只信任有效 ID，并从原始文本中切片。模型输出的主题和理由是辅助元数据，不能代替原文。

## 为什么需要上下文与 Lookahead

模型只看到从游标开始的固定 X 字，可能无法判断当前主题是否将在窗口之后立刻结束，也可能把上一段遗留的指代误认为新主题。可以给它：

- 上一个 Chunk 的主题与简短摘要；
- 当前窗口的完整单元；
- 少量超过目标长度的向后内容，用来判断边界；
- 明确的硬上限，禁止选择过远位置。

这比每次机械地截取恰好 X 字更容易找到稳定边界。必要的上下文可以作为元数据或检索时的父级内容补回，不一定要把大量重复文字写进每个 Chunk。

## 完成切片后的处理

每个最终 Chunk 应至少保存：

```text
chunk_id
parent_topic_id
start_unit_id / end_unit_id
speakers / timestamps
topic / summary
previous_chunk_id / next_chunk_id
source / version
content
```

完成且验证切片后，再为每个 Chunk 生成能够由它独立回答的典型 Question，并建立 question → chunk_id → content 映射。问题生成应基于最终 Chunk；如果之后又改变边界或正文，关联问题、摘要和向量都需要重新生成。

会议记录还可以针对决策、行动项、负责人、时间与争议点生成结构化元数据，但提取结果仍应指回具体的发言单元作为证据。

## 质量检查

- 主体切分范围连续覆盖全部原文，无遗漏或意外重复；若另加上下文重叠，明确标记重叠范围，不能把有意重叠误报为重复错误；
- 每个边界都位于真实句子或发言轮次之间；
- Chunk 不超过硬上限，过短 Chunk 有明确理由或被合理合并；
- 单个 Chunk 尽量主题集中，跨 Chunk 的主题延续有显式标记；
- 决策、条件、否定、数字和责任人没有因切分而失去上下文；
- 合成 Question 能够由对应 Content 独立回答；
- 用真实会议查询评估正确 Chunk 的 Recall@K，而不是只凭人工阅读判断切片是否自然。
