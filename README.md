# 🌌 Knowledge Star-Map（知识星图）

> 知识之所以有力量，是因为它们在乱序中连点成线。

Knowledge Star-Map 是一个以 Markdown 文件保存内容、Obsidian 提供阅读与导航、Git 管理版本、AI 助手参与学习和整理的个人知识系统。它的首要目标是把日常学习中的外部输入，转化为可以长期积累、连接和调用的个人知识；并在此基础上记录小说、写作、产品或其他方向的灵感。

仓库根目录同时是 Obsidian Vault。目录区分内容用途，笔记保存知识，MOC 组织关系，来源记录保存学习过程，协作规范约束助手如何工作。

## 目录职责

| 目录 | 职责 | 是否进入默认知识图谱 |
| --- | --- | --- |
| `00_Inbox/` | 快速捕获、等待整理 | 否，整理时可临时加入 |
| `10_Knowledge/` | 已整理、可复用的知识内容 | 是 |
| `20_Sources/` | 原始资料和来源笔记 | 否 |
| `30_Ideas/` | 小说及其他创意种子 | 是 |
| `40_Projects/` | 正在孵化或推进的具体成果 | 否 |
| `80_Local/` | 仅本机使用的课件、数据和临时实践，整个目录不提交 Git | 否 |
| `90_Archive/` | 已结束、过时或冻结的内容 | 否 |
| `99_System/` | 模板、附件、脚本和系统说明 | 否 |

完整的一级、二级、三级文件夹职责与归档规则见 [目录结构说明](99_System/目录结构说明.md)。新增、移动、重命名、删除目录或改变目录用途时，应在同一次修改中同步维护该说明；仅增改文件且未改变目录职责时，无须更新目录清单。

仅供本地实践的课程资料放在 `80_Local/Courses/`，课程出处、获取方式和学习进度仍保存在 Sources。该目录不会随 Git 克隆到新设备，需按 [本地工作区说明](99_System/目录结构说明.md#本地工作区) 重建；“可清理”不代表自动删除。

## 知识流转

```text
外部材料、学习讨论与想法
   ├── 来不及判断性质 → 00_Inbox
   ├── 长期原始资料、来源与进度 → 20_Sources
   ├── 本机课件、demo 与临时练习 → 80_Local（不提交 Git）
   ├── 已整理、可复用的认识 → 10_Knowledge/Notes
   └── 创意种子 → 30_Ideas

来源记录 ──提供依据──→ 知识正文 ←──组织入口── MOC
知识与灵感 ──支持明确成果──→ 40_Projects
已结束、过时或冻结的内容 ──按需归档──→ 90_Archive
```

这些是内容分流和引用关系，不是每份资料必须依次经过的步骤。性质明确时可直接放入对应目录。`Sources` 为知识提供依据，`Knowledge` 与 `Ideas` 构成正式知识星图，它们共同为 `Projects` 提供参考。

进入 Knowledge 不等于已经完全内化：笔记成熟度、事实核验状态与个人掌握程度分别判断。`developing` 笔记可以保存已整理的认识；不确定结论需标明边界，个人掌握情况记在学习接续中。

## 四类学习内容怎样分工

| 类型 | 主要回答什么 | 保存位置 |
| --- | --- | --- |
| 概念笔记 | 是什么、为什么、何时适用？ | `10_Knowledge/Notes/` |
| 案例笔记 | 对具体输入怎样处理，结果如何得到？ | `10_Knowledge/Notes/`，按主要问题归属 |
| 来源笔记 | 内容来自哪里、实际读了什么、学习到哪里？ | `20_Sources/Notes/` |
| MOC 内容地图 | 从哪里进入、先读什么、知识之间有什么关系？ | `10_Knowledge/Maps/` |

通用解释集中维护，案例保留必要输入和完整推理，地图提供阅读路线。学习日期、实际作答和个人掌握证据保留在来源记录中。具体分工示例见 [Query 改写在知识库中的位置](99_System/知识库组织与工作流程说明.md#用-query-改写理解内容分工)。

## 组织原则

- 顶层文件夹区分内容用途；`Notes/` 下按稳定主题群存放正文，不强迫知识只属于一个学科。
- Properties 记录笔记类型、状态和领域。
- `[[双向链接]]` 表达知识、来源和灵感之间的关系。
- MOC（Map of Content）人工组织领域和主题脉络。
- 标签主要用于 `#待整理`、`#待验证` 等临时工作状态。
- 知识笔记按独立问题划分；概念独立成篇，案例保留完整推理，MOC 组织阅读。通用解释集中维护，允许理解当前语境所需的简短复述。
- 复杂笔记采用金字塔原理组织表达：先回答核心问题，再按清楚的分组和逻辑顺序展开理由、过程与证据；关键条件和不确定性随结论保留。

颗粒度、概念与案例分工、[复杂笔记的表达方法](99_System/知识笔记组织规则.md#复杂笔记按金字塔原理组织)及整理验收标准见 [知识笔记组织规则](99_System/知识笔记组织规则.md)。

内容组织直接参考 [金字塔原理：结构化思考与表达](10_Knowledge/Notes/Thinking/金字塔原理：结构化思考与表达.md)。对分组、概括或推理顺序拿不准时，按[查阅顺序](99_System/知识笔记组织规则.md#方法依据与不确定时的查阅顺序)从总览进入专项方法，必要时回原书核对。

主题导航采用“浅目录 + 按问题组织的 MOC”：新主题先在已有地图中长成章节，有独立、长期导航价值时再建立专题地图，不因笔记增加或课程结束自动建图。具体标准见 [MOC 创建与维护规则](99_System/MOC创建与维护规则.md)。

## 五大学科 MOC

五大学科作为导航视角保留在 `10_Knowledge/Maps/Domains/`：

- Constants：形式科学，提供思维工具。
- Matter：自然科学，研究自然现象。
- Tides：社会科学，研究人类社会。
- Echoes：人文学科，研究精神与价值。
- Engines：应用科学，把知识转化为现实方案。

学科归类通过 `domains` 属性和领域 MOC 表达，一篇笔记可以同时被多张领域或主题 MOC 引用。正文按主要问题存放于 `Notes/AI/`、`Notes/Law/`、`Notes/Thinking/` 等主题目录，无须再建立五套学科文件夹。独立笔记暂留 `Notes/` 根目录时仍需属性与导航入口，位置在根目录不表示尚未分类。

## AI 跨学科主题域

AI 不作为第六个学科，而是由 [AI 主题地图](10_Knowledge/Maps/Topics/AI/AI.md) 统领的跨学科主题域。其范围涵盖传统机器学习、深度学习、表示／表征学习、推荐与偏好预测，以及相关工程、应用、产业和治理；主题范围与主线归档边界集中维护在 [目录结构说明](99_System/目录结构说明.md#跨层级归档规则ai)。AI 知识按主要问题分为六条主线：

| 主线 | 主要问题 | 笔记目录 |
| --- | --- | --- |
| 基础理论 | AI 的数学、统计和计算基础是什么？ | `01_Foundations/` |
| 模型与训练 | 模型与预测方法如何构成，以及怎样训练、推断、对齐和生成结果？ | `02_Models/` |
| 工程系统 | 如何构建可靠、可评估和可部署的 AI 系统？ | `03_Engineering/` |
| 应用实践 | AI 怎样解决具体任务和工作流问题？ | `04_Applications/` |
| 产业与商业 | AI 如何形成产品、商业模式和产业链？ | `05_Industry/` |
| 安全、治理与影响 | AI 带来了哪些风险、制度挑战和社会影响？ | `06_Governance/` |

AI 笔记只选择一个主要目录，同时通过 `topics`、`ai_area`、`domains`、MOC 和双向链接表达其他关系。公司、模型品牌和产品名称使用 Properties，不建立长期目录。

发布、融资、价格和市场份额等时效性事实先进入 `20_Sources/Notes/AI/Industry/` 并记录 `as_of`；只有提炼出的可复用认识进入 Knowledge。

## 与 GPT 一起学习

本项目通过根目录 [AGENTS.md](AGENTS.md) 保存项目上下文，通过 [knowledge-study](.agents/skills/knowledge-study/SKILL.md) 保存学习协作流程。在具备本项目文件访问能力的会话中，可以直接发送课程内容、问题或自己的理解。

学习会话默认边讨论边整理笔记：核对理解、复用已有知识节点、记录来源，并在课程来源笔记中维护“学习接续”。说“只讨论，先别写”可暂停保存；说“继续上次的某主题”可读取已记录的进度。默认不自动提交或推送 Git。

常规流程是：定位已有内容 → 解释与核对 → 查证关键主张 → 增量保存 → 检查文件 → 更新学习接续。下次继续学习时，根据对应来源记录恢复进度；普通提问不强制转成测验。

明确要求“review 这小节学习笔记”时，按 [Review 执行规范](99_System/学习小节Review规范.md) 检查本节及直接关联的旧笔记。报告分为“审核了哪些文件、待调整内容、问题解决进度”，完整证据放在附录。Review 默认只读；要求“解决 F01”或“review 并修正”后再落实相应修改。
