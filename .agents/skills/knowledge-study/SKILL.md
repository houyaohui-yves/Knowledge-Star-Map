# 学习讨论与知识沉淀

在当前 Knowledge Star-Map 仓库内使用。以仓库根目录的 `AGENTS.md` 为协作约定、`README.md` 为结构说明；路径均相对仓库根目录。不要依赖之前聊天历史或固定的本机绝对路径。

## 进入主题

1. 从用户当前问题确定主题、已提供的材料与希望解决的困惑。资料不足时先回答能够回答的部分；仅在缺失信息影响判断时补问，不要求填写开课表。
2. 搜索相关 MOC、知识笔记和来源笔记，兼顾中英文名称和同义词。对视频或课程，优先复用同一来源笔记；同一课程的不同章节可以记录在同一文件，过长时才拆分。
3. 用户明确继续某次学习时，读取对应来源笔记的“学习接续”；多个候选无法区分时询问课程或主题。不使用一个全局“当前学习”文件覆盖多个会话的进度。

## 帮助核对理解

- 先回应用户具体的理解或疑问：哪里成立、哪里混淆、需要什么前提，以及更准确的表述。保持跟得上视频的讨论节奏，按需要深入。
- 优先用一个贴近主题的例子或反例区分相似概念。关键误区可以邀请用户用自己的话复述或做一次小推演，不把每轮对话变成测验。
- 区分概念解释和事实核实。对不确定、专业细节、最新信息及高风险事实，按需核对官方文档、论文或权威资料；记录实际查阅的来源。无法核实就标记待验证，不编造引用。
- 对视频只依据实际可访问的片段、字幕或用户转述。仅有标题或链接不代表已经观看；转述标为“用户转述，未核对原视频”，助手补充单列。
- 法规、价格、版本和产品能力等记录适用范围与信息日期。`as_of` 是信息对应的有效时间，不能用访问日期冒充；必要时另记访问日期。
- 正式知识笔记保持客观表述。只有用户实际表达过的理解才能写成“我的理解”；仍有偏差的原话应放在“曾经的误区”并附纠正，而非写成结论。

## 何时写入

遵循项目中默认的边学边记授权：一个知识点形成清晰结论、重要误区得到纠正，或用户要求整理时，实际更新文件。没有实质新内容无需写入；用户明确仅讨论时不写。

尚未核实的材料可记在来源笔记的“待验证”，主题或来源都未明确时放 Inbox；不要把猜测提升成确定知识。不必等整节课结束才记录，也不要仅承诺稍后记录。

## 内容去向

| 内容 | 默认位置 |
| --- | --- |
| 课程、视频的要点与学习进度 | `20_Sources/Notes/Courses/` |
| 书籍、文章的来源记录 | `20_Sources/Notes/Books/`、`20_Sources/Notes/Articles/` |
| AI 发布、融资、定价等事实 | `20_Sources/Notes/AI/Industry/` |
| 可复用的概念、解释、条件与误区 | `10_Knowledge/Notes/` 对应主题 |
| 小说、幻想及其他想法 | `30_Ideas/Fiction/` 或 `30_Ideas/General/` |
| 尚未厘清的片段 | `00_Inbox/` |

明确要开展项目时才进入 Projects；复盘中提炼出的通用知识仍进入 Knowledge。

AI 主题沿用现有六条主线，`ai_area` 对应为：

| 目录 | ai_area |
| --- | --- |
| `01_Foundations/` | `foundations` |
| `02_Models/` | `models` |
| `03_Engineering/` | `engineering` |
| `04_Applications/` | `applications` |
| `05_Industry/` | `industry` |
| `06_Governance/` | `governance` |

新笔记按它主要回答的问题归类；跨主线关系通过真实的内部链接与 MOC 表达，选择最直接的 MOC 加入即可，不要求每条新笔记都更新 Home 或五大学科总览。

## 笔记质量与属性

- 按内容读取 `99_System/Templates/知识笔记模板.md`、`AI知识笔记模板.md`、`来源笔记模板.md` 或 `灵感模板.md`。实际写入时替换日期与标题占位符，略去无用空章节。
- 知识笔记以一个概念或判断为中心：核心认识、适用条件、一个必要例子、重要误区、真实关联与来源。保留学习形成的有价值解释，避免完整聊天转录或长篇照抄资料。
- 先更新现有同主题或空白 seed 笔记；不同名称但含义相同的内容通过别名或链接连接。遇到冲突先查依据；依据不足时记录争议，不覆盖原结论。
- 沿用 `type`、`status`、`topics`、`domains`；AI 笔记补充 `ai_area`。`domains` 取 Constants、Matter、Tides、Echoes、Engines，可多选。
- `seed` 表示待展开，`developing` 表示正在形成，`evergreen` 表示经过持续整理的稳定笔记，不能因本轮解释完毕就自动升级。成熟度不代表事实已核实或用户已掌握。
- 新笔记使用实际创建日期 `created`；更新时保留已有创建日期，必要时写实际 `updated`。不知道历史创建日期就不补造。
- 来源字段优先引用现有来源笔记；YAML 内部链接必须带引号，例如 `source: "[[课程名]]"`。多个来源可使用带引号的列表。引用网络资料时保留标题、实际 URL 和对应结论。
- 不为尚未出现的新概念批量生成占位文件，也不把实体名、公司或产品继续扩展成目录。

## 跨会话接续

在课程来源笔记中维护一个简短的“学习接续”段落。一个学习段落有进展或用户说“今天到这里”时更新：

- 最近学习日期与已知章节或时间戳；未知进度明确留空或说明未提供。
- 已讨论的核心问题与对应知识笔记链接。
- 用户实际表达的理解、已纠正的误区、仍未确认的掌握点。
- 待验证事项，以及下次可从哪里继续。

无明确来源时，可在 `00_Inbox/` 用有辨识度的日期与主题文件保存这些信息，注明“对话学习，无外部来源”。不创建虚构课程。不要自动保存整段私密对话或把所有会话汇总到一个不断膨胀的文件。

## 保存与反馈

写入后检查本次修改的 YAML、内部链接目标和 MOC 入口，确认没有重复笔记和未替换的模板占位符。只检查相关范围，不需要每轮全库扫描。

先给出对学习问题的回应，再用一句话列出已更新笔记的可点击链接；有未验证结论时明确指出。用户结束一段学习时简短汇总已学内容、遗留问题和接续位置。

默认不执行 Git 提交或推送。实际文件修改就是本次保存；如果当前会话没有工作区访问能力，只能交付草稿并说明未写入。
